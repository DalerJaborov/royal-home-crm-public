# Отсутствие сотрудника и автоматический выход — ограниченный проход

Проверка остановлена после одного воспроизводимого дефекта **TA-01**: тик выхода из отсутствия повторно проверяет срок, но не активность сотрудника. Если собственный синтетический сотрудник деактивирован после выборки кандидатов и до транзакции, тик всё равно снимает его отсутствие и сообщает о возвращении. **isActive остаётся false**: восстановление доступа или реальная выдача лидов этим воспроизведением не доказаны и не утверждаются.

Правки приложения не разрешались и не выполнялись. FINAL `4897ef97b3a935d69dff8e1610dbe77f79375430` и его полный прогон40047985891 не затрагивались. Эта находка ещё не является исправлением замороженного пакета и не добавляется молча к его реестру27семейств.

## Явный существующий контракт

- Докстринг `absenceReturn.ts:23–24`: «УВОЛЕННЫХ НЕ ВОЗВРАЩАЕМ: isActive=false — решение сильнее любой даты в календаре».
- Его исходная выборка `27–33` требует `isActive:true`, `frozenAt != null`, `absenceUntil != null && <= now`.
- Комментарий перед транзакцией требует повторной условной проверки после выборки, поскольку руководитель мог продлить/снять отсутствие. Транзакционный `updateMany` на строке55 повторяет только id/frozenAt/absenceUntil, **теряя isActive:true**.
- При count>0 вызывается существующий сдвиг часов неактивных клиентов; затем увеличивается returned, вызываются синхронизация очереди и сообщения сотруднику/руководителям о возвращении. Это побочные эффекты реального пути, а не результат одного лишь счётчика теста.

Прежний тест покрывает сотрудника, уже неактивного **до** выборки. Он не ловит показанное изменение между выборкой и условной записью. Здесь не вводится новая политика увольнения/доступов.

## Детерминированное воспроизведение TA-01

Собственная NEW БД `audit_team_absence`, клонированная из собственного `audit_template` в существующем изолированном PostgreSQL на127.0.0.1:15439. Другие БД не сбрасывались, не удалялись, соединения не прерывались. Все сотрудники — собственные синтетические AGENT; ни администратор, ни авторизация/пароль/2FA/elevation для этого helper-воспроизведения не требуются.

1. Создать активного сотрудника с `frozenAt=2030-05-26T04:00Z`, отпуском и `absenceUntil=2030-06-03T04:00Z`.
2. Запустить настоящий helper с явно переданным `now=2030-06-03T04:00Z`.
3. Узкая scheduling-подмена `prisma.agent.findMany` вызывает **настоящий SELECT**, сохраняет его результат и затем отдельной настоящей записью PostgreSQL коммитит `isActive=false` для этого собственного ID. После этого возвращает уже полученный список helper-у. Другие запросы/транзакция/условия не подменяются.
4. Helper выполняет настоящую транзакцию и `updateMany` в PostgreSQL.
5. Ожидание по явному контракту: returned0, отметки отсутствия сохранены, нет команды приветствия/синхронизации очереди.
6. **Факт:** returned1, isActive=false, frozenAt/absenceKind/absenceUntil=null; по одному вызову заглушенных push и queueSync.

Сохранённый обезличенный readback:

```json
{"scenario":"inactive-after-due-scan","result":{"returned":1},"isActive":false,"frozenAt":null,"absenceKind":null,"absenceUntil":null,"pushes":1,"queueSyncs":1}
```

Нормативная проверка падает `expected {returned:1} to deeply equal {returned:0}`. Это настоящий helper/БД с управляемым порядком выполнения; не настоящий HTTP-запрос деактивации и не одновременный production-процесс. Сам переход isActive=false выполнен напрямую для собственного fixture ID, без изменений прав/получения доступа. Push/queue не уходят наружу: их функции заглушены с сохранением остальных экспортов; fetch заменён бросающей заглушкой. Настоящих уведомлений/звонков/доставки не было.

### Дополнительная гипотеза снимка frozenAt

Координатор отметил: `shiftInactiveClockAfterAbsence` получает frozenAt из исходного снимка, а условная запись требует лишь not-null. Если заменить отсутствие другим с иным frozenAt, но всё ещё подходящим сроком, теоретически можно применить старую длительность. **Это не объявлено вторым подтверждённым багом.** Новый реальный freeze требует будущий until и ставит frozenAt в текущее время; future-extension-контроль выше как раз исключается текущим условием срока. Обычный достижимый HTTP-сценарий замены с уже подходящим deadline не доказан. Прямую произвольную порчу fixture-дат нельзя выдавать за доказательство такого клиентского пути. Дополнительная блокировка/сравнение frozenAt без отдельного обоснования в минимальный план не включены.

## Что остаётся непроверенным

Этот проход не выполнял HTTP/браузерные save/edit/manual-return: прочитан их контракт, но чтение не записано как исполнение. У текущего freeze API нет произвольного редактирования уже активного отсутствия: повторный freeze возвращает409; ручной unfreeze очищает срок и причину. API отклоняет прошлый until; shared-схема отдельно проверялась только на перечисленных входах. Поле «от/до» как отдельный диапазон в этом пути отсутствует — есть текущая отметка заморозки и необязательный момент выхода.

Не проверены физический телефон, настоящий администраторский UI, все списки/расчёты отсутствия, доставка push/АТС, межпроцессные расписания, production-данные или все состояния увольнения. TA-01 не объявляется обходом блокировки аккаунта: после воспроизведения isActive=false остаётся. Финальный полный прогон/реестр исправленных27семейств — ответственность координатора; эта новая неисправленная находка должна учитываться отдельно до решения о следующем пакете.
