# TA-01 — повторная проверка активности перед выходом из отсутствия

В `apps/api/src/lib/absenceReturn.ts` добавлено только `isActive:true` в существующий транзакционный `tx.agent.updateMany.where`. Если сотрудник деактивирован после предварительной выборки, условная запись теперь затрагивает0строк. Существующий путь count0 сохраняет отсутствие и клиентские часы, не вызывает возврат в очередь, не считает сотрудника вернувшимся и не готовит приветственные сообщения. Никакие права, даты/виды отсутствия, правила распределения или схема БД не менялись.

## Основание и исходный отказ

Явный действующий контракт в докстринге helper: «isActive=false — решение сильнее любой даты в календаре». Исходный SELECT это проверяет, но транзакционная запись повторяла только id/frozenAt/absenceUntil. Прежний тест проверял сотрудника, уже неактивного до SELECT; межшаговую деактивацию он не ловил.

Discovery в сохранённом PHASE2 дал1RED/5контролей на собственной БД. MAIN `NEXT-TEAM-ABSENCE-READONLY.md` сохраняет этот результат/границы; соответствующие файлы PHASE2 совпадали с FINAL4897. Для исправления координатор подготовил отдельный public worktree FINAL2 от `4897ef97b3a935d69dff8e1610dbe77f79375430`, собственные реальные node_modules, shared build и Prisma7.10.1. Исходный FINAL и его полный прогон40047985891 не менялись.

До правки прочитаны AGENTS/CLAUDE; их SHA совпали с прежним прочитанным FINAL. `where --file absenceReturn.ts` показал единственного исходного потребителя cron.ts; impact перечислил agent-absence, inactive-traffic-light-lost и два более широких cron-теста. Map/полный пакет/коммиты остаются у координатора.

Новая обычная регрессия `apps/api/tests/agent-absence-deactivation-race.test.ts` на неизменённом приложении подтвердила **native1:1FAIL/5PASS** (`team-absence-final2-red-r2.log`):

- настоящий SELECT получает собственного активного сотрудника с наступившим сроком;
- узкий scheduling hook коммитит настоящее `isActive=false` в PostgreSQL до настоящей транзакции helper;
- результат ошибочно returned1, frozenAt/причина/вид/срок очищены;
- клиентский inactiveSince реально сдвинут с20мая на28мая из-за восьми дней старого отсутствия;
- isActive остаётся false. Реактивация доступа/реальная выдача лидов этим не доказываются.

Общее ожидание строки/счётчика/часов падает на перечисленных фактических значениях, а не на проблеме импорта. Push и синхронизация очереди заглушены с сохранением прочих экспортов; настоящий внешний fetch запрещён бросающей заглушкой. Нет настоящих звонков, push, provider/config/production-действий. Деактивация выполнена напрямую только для собственного fixture ID, без изменения разрешений/паролей/2FA или обхода авторизации.

## Строгая итоговая фикстура

Собственная БД `audit_team_absence` на loopback15439, созданная в предыдущем проходе из собственного audit_template и очищенная по своим ID. Не сбрасывалась/удалялась; чужие БД/строки не затрагивались. Node24.20.0, Vitest4.1.12, Prisma client/adapter/CLI7.10.1; retry0.

Новые IDs и тестовые phone-ключи используют randomUUID на каждую подготовку, без Date.now-коллизий. Клиентский StageEvent после создания ожидается по конкретному собственному client.id перед последующей адресной очисткой.

По замечанию координатора и независимого review тестовое чтение кандидатов дополнительно ограничено captured agentIds через AND к исходному реальному условию. Схема SELECT узнаётся по select.absenceKind/frozenAt; запросы получателей и другие agent.findMany проходят неизменёнными. Настоящий SQL/условие/результат и настоящая запись деактивации сохраняются. Scheduling hook оборачивает только ожидаемый helper-ом query.then; тип на этой границе приведён к типу исходного query, без фиктивных PrismaPromise-тегов/глобального any.

В гонке дополнительно создаётся собственный **посторонний для списка кандидатов** сотрудник с наступившим сроком. Его полная строка должна остаться неизменной; строгие returned0 и нулевые push/batch/queue сохраняются. Это защищает прогон с остаточными данными другого файла, не очищая неучтённые чужие отпуска и не меняя глобальную политику helper-а.

Итоговые6случаев:

1. За1мс до срока — строка не меняется, возврата нет.
2. Точная граница — возврат1, поля отсутствия очищены; повторный тик0.
3. Бессрочный больничный и уже неактивный до SELECT — обе строки сохранены.
4. Подтверждённое продление между SELECT/транзакцией — новый срок сохраняется, возврата нет.
5. Существующая shared-схема сохраняет допустимый срок/null и отвергает короткую причину, неизвестный вид и не-дату.
6. Деактивация после SELECT — returned0; isActive=false, поля отсутствия и точный inactiveSince сохранены; push/batch/queue0; посторонний собственный due-witness не изменён.

Сама новая регрессия не импортирует cron/index/worker и не запускает расписания. Браузерные/HTTP save/edit/manual-return этой правкой не выполнялись. Гипотеза замены frozenAt не доказана обычным достижимым потоком и не добавлена в условие записи.
