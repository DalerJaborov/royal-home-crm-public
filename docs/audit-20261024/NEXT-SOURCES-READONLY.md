# Источники лидов — ограниченная проверка текущего контракта

Подтверждена одна новая неисправленная находка **SRC-01**: обычная переписка Telegram Direct канала до создания карточки клиента вообще исчезает из `/reports/sources`. Отчёт считает BotConversation и TelegramConversation, но не существующую отдельную таблицу TelegramDirectConversation. После фактического воспроизведения дальнейший поиск остановлен; разрешения на исправление не было, исходники/обычные тесты не менялись.

## Сначала — уточнение карты и возможностей

Карта `docs/product-map.md:89` ведёт `/sources` в `apps/web/src/pages/Sources.tsx`. Это **аналитика источников**, а не редактируемый справочник. Страница использует `useSourcesReport`→GET `/reports/sources`, отдельные маркетинговые/тепловые срезы и кнопку пересборки AI-разбора. Sources CRUD API, создания/архива/восстановления самих источников в этом пути нет. Допустимые источники — фиксированный shared `CLIENT_SOURCES` из11значений с `CLIENT_SOURCE_LABELS`.

Поэтому отсутствующие операции справочника не симулировались и не записаны в покрытие. Наличие всех11значений/подписей и принятие/отклонение source в существующей shared-схеме проверены отдельно; настоящее HTTP-редактирование source карточки не выполнялось. AI-пересборка, настройки каналов/аккаунтов, подключение провайдеров и финансовые/периодные проверки не вызывались. Прежние BUSINESS/coverage/периодные находки не повторялись.

## SRC-01 — ожидаемый контракт и причина

`apps/api/src/routes/reports.ts:347–359` прямо объясняет: отчёт должен видеть тех, кто написал и ушёл без телефона/заявки; иначе канал со множеством таких обращений выглядит пустым. Итоговое объединение sources включает переписочные каналы даже при total0. UI Sources показывает это через `wrote` и текст обращений.

Однако фактические запросы `reports.ts:360–367` читают только:

- BotConversation по channel;
- количество TelegramConversation за окно.

В схеме БД отдельно существует TelegramDirectConversation: личные сообщения **каналу**, с ключом chatId/topicId, в отличие от лички боту. Обычный `messengers/telegramDirectMessages.ts:146–159` сохраняет именно эту запись на первом сообщении до появления clientId. В том же действующем пути при последующем оформлении клиента `731–740` задаются source=`TELEGRAM`, channel=`TELEGRAM`. Путь не добавляет такой диалог в TelegramConversation. Этот модуль только читался, не импортировался/исполнялся в пробе.

Сильнейший пример не требует решений о повторных людях/атрибуции: **единственный Direct-диалог, никаких иных диалогов или клиентов**. Его пропуск противоречит заявленному включению написавших до заявки независимо от возможной будущей политики дедупликации.

## Настоящий HTTP/PostgreSQL — воспроизведение и контроли

Свежая собственная NEW БД `audit_sources TEMPLATE audit_template`, существующий собственный PostgreSQL на127.0.0.1:15439. Другие БД не сбрасывались, не удалялись и не останавливались. Синтетический DIRECTOR, обычный подписанный тестовый access token, никаких переопределений разрешений/elevation/паролей/2FA. Данные подготовлены напрямую через Prisma; проверка читает их через настоящее Express/auth/Prisma/HTTP.

Окно2020-06-01..2020-06-30 выбрано только для изоляции собственных записей, не для новой проверки периодов. Собственный TelegramDirectConversation имеет createdAt15июня в середине окна, clientId=null, отдельные UUID-ключи chatId/topicId. Провайдер/входящий handler/модель не вызываются.

Фактический ответ HTTP200:

```json
{"scenario":"telegram-direct-only-before-lead","sources":[],"directRows":1}
```
