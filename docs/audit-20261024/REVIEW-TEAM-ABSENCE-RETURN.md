## Минимальность и инварианты приложения

Единственное изменение приложения — `isActive:true` в существующем транзакционном `tx.agent.updateMany.where`. Условие уже есть в первоначальной выборке и прямо следует из документированного правила: неактивность сильнее даты выхода. Оно добавляет повторную проверку после первоначального SELECT; даты, включительная граница `<= now`, бессрочное отсутствие, правила увольнения/разморозки и алгоритмы назначения не меняются.

При деактивации между SELECT и UPDATE запись теперь возвращает count0. Существующий код сдвигает часы неактивных клиентов только при count>0 **в той же транзакции**, затем `if(count===0) continue` пропускает инвалидацию доступа, синхронизацию очереди, returned/имя и push сотруднику. Общая рассылка руководителям вызывается только при returned>0. Это закрытие побочных эффектов следует из прочитанной структуры кода; в новом runtime-регрессионном тесте непосредственно проверены нулевые вызовы трёх подменённых функций: push сотруднику, batch push и queue sync.

Helper **не устанавливает isActive=true** ни до, ни после правки. Исходное воспроизведение и новый тест сохраняют isActive=false. Это ошибка снятия отсутствия/сдвига часов/ложных сообщений о возвращении, **не доказанное восстановление аккаунта, реальное включение звонков или обход блокировки**.

Дополнительный frozenAt-stamp guard не добавлен: обычный достижимый сценарий новой заморозки с уже наступившим сроком не подтверждён. Гипотеза остаётся отдельно от TA-01; произвольная замена fixture-дат не выдаётся за продуктовый путь. Правка также не обещает остановить любое последующее изменение состояния уже после успешного выхода из отсутствия.

## Durable-тест и исправленная изоляция

Первоначальный draft нового файла вызывал глобальную выборку helper-а и проверял точные глобальные returned0/1. Независимое ревью и координатор выявили возможность вмешательства чужого due-agent fixture. Автор исправил **только test harness**:

- Spy распознаёт именно candidate SELECT по `select.absenceKind===true && select.frozenAt===true`. Остальные `agent.findMany`, включая получателей руководительского сообщения, идут в оригинальный Prisma delegate без фильтрации.
- Candidate SELECT исполняется реально в PostgreSQL: исходный `args.where` сохранён через `AND` с captured candidate IDs. Строки/UPDATE/транзакция не заменены объектами или in-memory адаптером. `query.then` управляет только расписанием: реальная деактивация/продление коммитятся после чтения кандидатов и до реального helper transaction. Обёртка используется текущим helper-ом как awaited query.
- Целевой race требует **строго** returned0, isActive=false, исходные frozenAt/reason/kind/until, **точно неизменный** inactiveSince собственного клиента и ноль push/batch/queue. Отдельный собственный due-agent witness исключён из кандидатов и сравнивается целиком с исходной строкой. Это защищает от ложного GREEN за счёт смены счётчика и от мутации свидетеля.
- Контроли: NOW−1ms, точная граница и повторный тик, бессрочный больничный, уже неактивный сотрудник, продление после SELECT, существующая schema validation. Положительная точная граница сохраняет isActive=true и ожидаемое очищение метаданных; очередь вызывается с точным собственным ID.
- Новый UUID создаётся при каждом makeAgent/client, включая retry; cleanup удаляет StageEvent только captured client IDs, затем собственных клиентов и только captured candidate/witness agent IDs. Ожидание исходного StageEvent собственного клиента предшествует cleanup. Нет глобального delete/reset чужих данных. Потенциальные реальные отправки заменены; throwing fetch guard проверен после каждого случая.
