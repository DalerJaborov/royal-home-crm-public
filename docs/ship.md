# Выкат на сайт: `npm run ship` — единственный путь

Введено 24.09.2026 по вопросу Dan: «надо железное правило, чтобы везде работало —
и вне этого чата, и в Claude Code». Действует для любой сессии: проект claude.ai,
Claude Code на ноутбуке, другая учётная запись.

На Windows при использовании Node 24.x команда выпуска требует **24.16+**:
версии 24.0–24.15 содержат исправленный в
[Node #62561](https://github.com/nodejs/node/pull/62561) дефект инициализации
Windows TCP, вызывающий случайный native crash `0xC0000409`. Ship блокирует
этот диапазон до миграций и проверок. Проверь `node --version` в том же терминале.
Допустим portable Node в PATH только процесса; менять глобальный Node или
production runtime ради проверки не требуется. Это не обход полного gate:
после смены runtime весь ship должен пройти заново. Совпадение кода аварии
само по себе не доказывает, что каждый crash имеет именно эту причину.

## Правило

1. **В `main` (= на сайт через минуту) правка попадает только командой
   `npm run ship`.** Вручную не вливать — ни кнопкой на GitHub, ни `git push` в
   `main`, ни инструментом «merge» из чата. Отметку «проверено» руками не ставить.
2. **Правки одной темы — по 2–3 в одну.** Каждое вливание делает все остальные
   открытые правки «несвежими», и каждой потом нужен свой полный прогон (~20 мин).
   Три мелочи одного экрана — одна правка, один прогон.
3. **По одной за раз.** В проекте claude.ai очередь ведёт координатор: тред
   запускает `npm run ship -- --no-merge`, шлёт координатору номер коммита и числа,
   по сигналу — `npm run ship` (он сводит и прогоняет всё заново на текущем
   `main`, ~25 мин; поэтому сигнал даётся, когда никто другой не вливает). Чат
   Claude Code на компьютере владельца с 02.10.2026 запускает `npm run ship` сам
   (Dan: «Разрешаю Claude на компьютере самому выкатывать на сайт»); если в это
   время влил кто-то другой, команда видит сдвинутый `main` и не вливает — её
   запускают заново.

## Что делает команда

| Этап | Что | Красное → |
|---|---|---|
| 1. подготовка | ветка не `main`, дерево чистое, есть доступ к GitHub, правка открыта | стоп, названо что |
| 2. свести | с `main` по **явному** sha (`sync-main.mjs --onto`); конфликт в `docs/product-*` — версия `main` + `npm run map` | стоп: конфликт в коде разводит человек |
| 3. режимы | нет ссылок (120000) и вложенных репозиториев (160000) | стоп |
| 4. миграции | `npm run prisma:generate` и `prisma migrate deploy` на тестовую базу — всегда: сведение с `main` приносит чужие миграции | стоп |
| 5. precheck | сборки, eslint, аудиты, карта, сторож карты, журнал, тесты фронта | стоп |
| 6. тесты API | полный прогон, 0 падений, отчёт обязателен | стоп |
| 7. отправить | ветку в GitHub, без силы | стоп: в ветке чужие коммиты |
| 8. отметка | строка `Ship-Verified: tree=<дерево> …` для squash-коммита; статус GitHub «проверено» — где GitHub даёт его поставить | — |
| 9. влить | squash со строкой-отметкой, только если `main` всё ещё тот sha | стоп: `main` ушёл, ship заново |
| 10. после | дерево `main` = проверенному побайтно; иначе `build:api`, `build:web`, `map:check` на `main` | громко: чинить вперёд очереди |

Ключи: `--dry-run` (план и препятствия, ничего не меняет), `--no-merge` (остановиться
перед вливанием), `--full` (полный прогон всегда), `--clean-db` (прогон на новой пустой
базе `rh_clean_<время>` — когда тестовая база засорена; `migrate reset` не нужен),
`--pr=N`.

**Красный полный прогон останавливает ship.** Код процесса должен быть 0, а
обязательный отчёт `runParallel` — зелёным, с тестами и без падений. Повтор
упавших файлов по одному помогает найти причину, но не разрешает выкат: рядом
могли быть авария worker или незавершённые тесты. После исправления нужно
запустить полный `npm run ship` заново. Автоматического допуска по зелёному
повтору отдельных файлов и отметок `flaky=N` больше нет.

**Правило «пачки» — когда полный прогон тестов сервера не нужен** (решение Dan
24.09): правка не трогает ни `apps/api` (кроме самих файлов `*.test.ts`), ни
`packages/`, ни корневые `package.json`/`package-lock.json`. Тогда precheck
гоняет тесты, задетые правкой по импортам, — в том числе изменённые `*.test.ts`.
Решает скрипт сам по списку файлов и пишет причину в выводе.

## Почему после каждого вливания «всё заново» — и почему это не страшно

Так делают все, кто выкатывает с `main` автоматически: проверяется не правка сама
по себе, а **правка поверх текущего `main`**. Две зелёные порознь правки дают
красный `main` — у нас так было с картой продукта (#887) и с типами (#643/#651).
Поэтому GitHub требует, чтобы ветка была свежей (`strict`), а отметка стояла на
последнем коммите.

Перепроверяет машина, не человек. Чтобы это не стоило часов:

- правки мелких тем копятся по 2–3 в одну (пункт 2 правила);
- правка сайта или только тестов идёт без полного прогона сервера (правило «пачки»);
- после вливания `main` не пересобирается, если его дерево побайтно равно
  проверенному — а при свежей ветке и squash так и есть всегда;
- ускорение самого полного прогона — отдельная правка (docs/journal).

У крупных команд то же самое называется «очередь вливания» (merge queue): машина
берёт правки по одной, сводит с `main`, гоняет проверки и вливает только зелёные.
`npm run ship` — это она, только запускаемая командой, потому что проверки
GitHub Actions у нас с 22.09 не запускаются.

## Отметку проверяет сервер (выбор Dan 24.09)

Отметка «проверено» — строка в сообщении squash-коммита:

```
Ship-Verified: tree=<дерево проверенного коммита> main=<sha> api-tests=<N> failed=0
```

Сервер выката (`ops/auto-deploy.sh`, функция `crm_ship_verified`) берёт на сайт
только вершину `main`, у которой эта строка есть и `tree=` совпадает с настоящим
деревом коммита. Дерево — это побайтно всё содержимое, поэтому совпадение значит:
на сайт едет ровно проверенное. Влили мимо команды — сайт остаётся на прежнем,
в журнал сервера пишется строка, в Telegram один раз уходит «⛔️ влито мимо
проверки». Следующий `npm run ship` проверит `main` вместе с этим коммитом и выкатит
всё разом. Снять сторожа на время (разбор руками на сервере):
`CRM_AUTODEPLOY_SHIP_GATE=0`.

Почему не обязательной проверкой GitHub: облачные сессии Claude не могут ставить
статусы GitHub — их прокси запрещает запись в `/statuses` и `/check-runs`
(403, проверено 24.09). Обязательный статус закрыл бы `main` для всех тредов
проекта. Статус «проверено» команда всё равно ставит там, где можно (ноутбук), —
для глаз.

## Защита `main` на GitHub (Dan сказал «да» 24.09) — на этом тарифе недоступна

**25.09.2026 проверено с ноутбука владельца:** GitHub отвечает 403 «Upgrade to
GitHub Pro or make this repository public to enable this feature» — приватный
репозиторий на бесплатном тарифе не даёт ни защиту веток, ни rulesets. Поэтому
`main` держит только сервер (раздел выше), и этого достаточно: влитое мимо
команды на сайт не едет. Ниже — что включить, если тариф когда-нибудь сменится.


Держит то, что сервер не видит: в `main` только правкой и только squash, без
переписывания истории, без исключений. `npm run protect:main` показывает
настройки, `npm run protect:main -- --apply` включает (нужен доступ владельца —
`gh auth login` на ноутбуке; облачной сессии GitHub настройки защиты не отдаёт,
403). То же руками: github.com → репозиторий → Settings → Branches → правило для `main`:

- ☑ Require a pull request before merging — одобрений **0** (проверяет машина);
- ☐ Require status checks — **не включать** (см. выше: проверяет сервер);
- ☑ Require linear history (только squash);
- ☑ Do not allow bypassing the above settings (правило и для владельца);
- ☐ Allow force pushes, ☐ Allow deletions.

Что остаётся на честном слове: строку `Ship-Verified` технически может написать
руками любой, у кого есть право вливать. Пишет её только `scripts/ship.mjs`, и
сервер сверяет её с деревом коммита — подделка должна быть осознанной.
