# План: своя переписка WhatsApp на каждый наш номер (26.11.2026)

## Цель владельца
«Один бот, одно ядро отвечает всем везде, без ошибок». У второго номера WhatsApp (Arvan,
phone_number_id 1476112588909838, строка `MessengerAccount` brandName «Арван») имя своё.

## Что сломано сейчас (ФАКТ, код main cbf6f4279)
- `BotConversation @@unique([channel, subscriberId])` (Gate A) общий на канал. В WhatsApp собеседник
  — это номер телефона, поэтому человек, уже писавший на Royal Home (номер в Настройках), при
  письме на Arvan упирается в свою старую переписку.
- Обход #475: `customerAgentEnrollment` удерживает такой ход (`whatsapp_peer_on_other_number`),
  `customerHeldMessage` кладёт текст в переписку Royal Home, бот молчит, сотрудник отвечает
  с номера Royal Home (чужое имя, чужое окно 24 ч).
- Всё остальное уже готово к разделению: каждая строка `BotConversation` получает
  `endpointScopeId` (триггер `customer_native_scope_insert`), есть `@@unique([endpointScopeId,
  subscriberId])`, отправка и ответы ищут переписку по области (`findScopedBotConversation`,
  `loadCustomerTransportForConversation`), окно 24 ч уже считается по номеру
  (`whatsappFirstContact.lastClientWhatsAppMessageAt`).

## Решение
1. **Миграция** `20261126190000_whatsapp_chat_per_number`: снять глобальный уникальный ключ
   `BotConversation_channel_subscriberId_key`; вместо него частичный уникальный
   `(channel, subscriberId) WHERE channel <> 'WHATSAPP'` (Instagram, Facebook, сайт, YouTube —
   как было) и обычный индекс `(channel, subscriberId)` для поиска. WhatsApp держит
   уникальность по `(endpointScopeId, subscriberId)`. Данные не меняются: 1262 переписки
   уже уникальны и остаются как есть. Из схемы Prisma уходит `channel_subscriberId` — все
   обращения по нему ломают сборку (сторож), их 3 в коде и 27 в тестах. Тот же двойной ключ
   (старый на канал + новый по области) есть у спутников переписки — щита исходящих
   `OutboundShieldState` и отметок показов `ShownProperty`; им та же правка, иначе ответ бота во
   вторую переписку упрётся в `compat_collision` щита.
2. **Одна дверь** `customerConversationScope.ts`:
   - `whatsappChatPerNumber()` — рубильник `WHATSAPP_CHAT_PER_NUMBER` (по умолчанию ВКЛ,
     `off` возвращает поведение #475: одна переписка на человека, ход на второй номер
     удерживается и текст ложится в старую переписку).
   - `peerChatsForScope()` — какие переписки этого человека мешают переписке в данной
     области. Переписка WhatsApp на ДРУГОМ нашем номере (область `NORMAL`) не мешает;
     старые переписки без номера (`LEGACY_UNKNOWN`) и любые чужие в Instagram/Facebook
     мешают, как раньше.
   - `ensureScopedBotConversation`: для WhatsApp — замок на номер собеседника
     (`pg_advisory_xact_lock`), проверка через `peerChatsForScope`, вставка. Новая переписка
     сразу получает карточку клиента, если у всех переписок этого номера WhatsApp ровно одна
     живая карточка (номер — подтверждённый транспортом признак человека).
3. **Чтения по (channel, subscriberId)** переведены на правило выше:
   `customerAgentEnrollment` (решение «ядро/старый бот/удержать»),
   `customerAgentLegacyCutover` (готовность к переводу на ядро), `metaSendBlock`
   (передача ждущей переписки человеку — по аккаунту), YouTube-архив (без `upsert`).
4. **Обход #475 убран из основного пути**: при включённом рубильнике
   `whatsapp_peer_on_other_number` не возникает; код удержания остаётся только как
   поведение выключенного рубильника.
5. **Выбор номера для старых отправок без сохранённого транспорта**
   (`resolveLegacyMetaSendTransport` → `sharedTokenNamespaceOfPeer`): номер выбирается по
   переписке; если у человека переписки на двух номерах — отказ (`account_mismatch`),
   без догадки. Все ответы бота и сотрудника из экрана переписки идут с сохранённым
   транспортом переписки и этим путём не ходят.
6. **Экран**: список переписок уже показывает название аккаунта («Arvan · +992 …»), когда
   аккаунтов больше одного (`RoyalDialogRow`/`MobileChatsList`, `accountTitle`). Карточка
   клиента получает обе переписки через `clientId`.

## Пред-мортем (что может сломаться)
| Риск | Защита |
|---|---|
| Код ждёт одну переписку на (канал, номер) и молча берёт не ту | Тип `channel_subscriberId` убран — сборка ловит; сырые SQL просмотрены (список в журнале) |
| Две параллельные первые реплики на разные номера | Замок на номер собеседника + уникальный по области |
| Переписка «без номера» (LEGACY_UNKNOWN) раздвоится | `peerChatsForScope` считает её мешающей — как раньше |
| Откат кода после разделения | Глобальный ключ вернуть нельзя, пока есть пары; откат — рубильником `off`, не миграцией |
| Instagram/Facebook поменяют поведение | Частичный уникальный ключ и прежняя проверка для них не тронуты, тест |

## Проверка
Тесты на настоящей базе (portable Postgres): «один человек на двух номерах → две переписки,
ответ с правильного номера и от бренда», рубильник `off` = поведение #475, LEGACY_UNKNOWN
не раздваивается, Instagram без изменений, существующие тесты удержания/аккаунтов/ядра.

## Что остаётся после
- Старые служебные отправки WhatsApp без транспорта (напоминания и т. п.) человеку с двумя
  переписками откажут — перевести их на транспорт переписки.
- Звонки на второй номер — правка шлюза `ops/whatsapp-gateway` (отдельное «да»).
