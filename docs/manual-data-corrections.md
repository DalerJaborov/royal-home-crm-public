# Ручные исправления бизнес-данных — П-12

Обычные формы CRM продолжают работать по своим правам. Внештатное исправление базы выполняется через зарегистрированную операцию и проверяемый план, с указанием автора и причины. Прямой произвольный SQL не заменяется «универсальным редактором» с обходом владения, проверок или KPI.

Текущий реестр разрешает только `CLIENT_LABELS` — уточнение имени/фамилии. Владельцы, роли, телефоны, статусы, СБ, задачи и деньги не входят в разрешённые поля. Для новой операции нужен отдельный обработчик с существующими доменными сервисами, перечнем читающих механизмов и регрессиями. Поддержка этого процесса не означает разрешение выполнить какую-либо правку production.

1. Проверить основание, согласование и актуальную резервную копию. Подготовить локальный JSON: requestKey(UUID), operation=CLIENT_LABELS, reason(не менее20символов), targets[{clientId,patch:{fullName/lastName}}]. Не сохранять реальные данные, причины и токены в Git.
2. Запустить скрипт `apps/api/scripts/clientDataCorrection.mjs --input=...`. Адрес API и обычный access token задаются в окружении CRM_MAINTENANCE_API_BASE/CRM_MAINTENANCE_ACCESS_TOKEN. Нет прямого подключения к базе; действуют авторизация CRM, роли ADMIN/DIRECTOR, права настроек и видимости телефонов. По умолчанию это DRY_RUN, без записи даже плана.
3. Добавить --output-preview=/приватная-папка/новый-файл.json и проверить конкретные старые/новые значения и инвентаризацию читающих модулей. Для сохранённого плана есть --review --plan-id=... с таким же выводом в файл. Файл создаётся исключительно новым, вне Git, с режимом0600; на Windows необходимо использовать закрытую папку профиля с соответствующими NTFS-правами (POSIX-режим не заменяет ACL). Значения и причина не печатаются в консоль. Инвентаризация консервативно ищет имена полей в установленном коде и включает планировщик; одноимённые поля сотрудников тоже попадают в список. Это проверяемый список для оператора, не обещание полного статического анализа динамических эффектов. Отпечатки кода/данных закреплены в плане.
4. `--persist-plan` сохраняет план и снимок исходных значений; карточки ещё не меняются. План принадлежит аутентифицированному автору, действует30минут. Любая параллельная правка карточки или изменение читающего кода требует нового плана.
5. Применение закрыто по умолчанию. Для будущего согласованного исполнения нужны server gate MANUAL_DATA_CORRECTIONS_LIVE=explicitly-approved, операторский CRM_MAINTENANCE_ALLOW_APPLY=explicitly-approved и параметры --apply --review-impact --plan-id=... --plan-hash=.... Не включать эти разрешения для проверки данной версии; тесты используют отдельную базу.
6. Изменения, системная история с именем реального оператора, AuditLog и результат плана коммитятся одной транзакцией с контрольным чтением. При конфликте откатываются все карточки. Закрытая причина остаётся в приватном плане, не раскрывается агентам в истории. Повтор того же применения возвращает сохранённый результат и не пишет вторую историю.
7. При обрыве ответа не придумывать результат: `--status --plan-id=...` читает состояние плана. Нельзя автоматически повторять операции другим планом. После исполнения проверить результат и читающие фоновые механизмы. Откат — отдельное согласованное исправление с новым текущим снимком; не восстанавливать старую БД поверх новых действий CRM.
