# 26.11.2026 — WhatsApp: своя переписка на каждый наш номер (Royal Home и Arvan)

- **Что изменилось.**
  1. Миграция `20261126190000_whatsapp_chat_per_number`: общий на канал уникальный ключ `(channel, subscriberId)`
     снят у `BotConversation`, `OutboundShieldState` и `ShownProperty` (`(channel, recipientId, shortId)`); вместо него
     частичные уникальные ключи «вне WhatsApp» (Instagram, Facebook, сайт, YouTube — как было) и обычные индексы для
     поиска. WhatsApp держит уникальность по области номера: `(endpointScopeId, subscriberId)`. Данные не меняются.
     У щита есть ещё ключ строк без области (`WHERE "endpointScopeId" IS NULL`) — его выбирает старый `ON CONFLICT`.
  2. `lib/customerConversationScope.ts` — одна дверь: `peerChatsForScope` (какие переписки человека мешают переписке
     этого номера: другой наш номер WhatsApp не мешает, переписка «без номера» LEGACY_UNKNOWN и чужие в
     Instagram/Facebook мешают), `readPeerChats`, рубильник `whatsappChatPerNumber()` (`WHATSAPP_CHAT_PER_NUMBER`,
     по умолчанию ВКЛ). `ensureScopedBotConversation` для WhatsApp берёт замок на номер собеседника, проверяет правило и
     сразу привязывает новую переписку к карточке клиента, если у переписок этого номера ровно одна живая карточка.
  3. По тому же правилу: `customerAgentEnrollment` (решение «ядро / старый бот / удержать»), `customerAgentLegacyCutover`
     (готовность к переводу на ядро), `metaSendBlock` (передача ждущей переписки человеку — переписка того аккаунта,
     с которого шла отправка), `propertyShowcase` (отметки показов в режиме compat), YouTube-архив без `upsert`.
  4. Обход #475 (`whatsapp_peer_on_other_number`: текст на Arvan ложился в переписку Royal Home, бот молчал) больше не
     срабатывает; остался только как поведение выключенного рубильника.
  5. `customerMetaTransport.sharedTokenNamespaceOfPeer`: у человека переписки на двух номерах — отправка без сохранённого
     транспорта получает отказ, номер не угадывается. Ответы бота и сотрудника из экрана переписки идут с транспортом
     своей переписки.
- **Почему.** Владелец: «один бот, одно ядро отвечает всем везде, без ошибок»; у Arvan своё имя. В WhatsApp собеседник —
  номер телефона, и человек, писавший на Royal Home, не мог получить ответ от Arvan с номера Arvan.
- **Найдено по классу (баг = класс).** Кроме `BotConversation` тот же двойной ключ был у щита исходящих и отметок
  показов: без их правки вторая переписка заводилась бы, а ответ бота в неё упирался бы в `compat_collision` щита
  (бот молчит), отметка показа объекта не писалась бы. Сырые SQL по `(channel, subscriberId)` просмотрены: остальные уже
  идут по области или по `id` переписки (список в `docs/plan-whatsapp-chat-per-number-26-11.md`).
- **Чем проверено.** `tests/whatsapp-chat-per-number.test.ts` на настоящей базе (portable Postgres): один человек на
  двух номерах → две переписки, ответ с правильного номера и токена, бренд «Арван», одна карточка клиента; щит и
  отметки показов по номеру; гонка первых сообщений; рубильник `off` = поведение #475; LEGACY_UNKNOWN не раздваивается;
  Instagram по-прежнему одна переписка (и база отказывает дублю). Проверка «ломаем нарочно»: с рубильником `off`
  первый тест красный. Плюс `whatsapp-second-number`, `whatsapp-shared-token-send` и 17 тестов, переведённых с
  `channel_subscriberId` на `findFirst`.
- **Что осталось.**
  - Старые служебные отправки WhatsApp без транспорта переписки (например, `lib/buyerGuide.ts`) человеку с двумя
    переписками откажут (`account_mismatch`) — перевести на транспорт переписки.
  - Откат: после первой пары переписок глобальный ключ миграцией не вернуть; откат поведения — `WHATSAPP_CHAT_PER_NUMBER=off`
    в `.env.production` (правка конфига прода — отдельное «да»).
  - Область номера Arvan отметить в «Новый бот» (ядро), звонки на второй номер — правка шлюза (см. журнал #475).
