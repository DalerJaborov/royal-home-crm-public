# 25.11.2026 — Загрузка видео и фото: не теряется молча, человек видит МБ, скорость, причину (волна A, только apps/web)

Владелец: «загрузка никогда не теряется молча; человек всегда видит, сколько МБ из скольки,
скорость, сколько осталось, что случилось и почему, и есть „Повторить“». Поводы — Android,
ролики 219–271 МБ из галереи («Телефон не даёт прочитать файл… попытка 1/10, статус 0») и
аудит пяти клиентских реализаций загрузки. Сервер (план частей, Caddy) — параллельные волны,
здесь не трогали.

## Что изменилось (по номерам находок аудита)

- **Общие кирпичи `apps/web/src/lib/upload/`**: `readProbe.ts` (чтение файла с причиной),
  `wakeLock.ts` (экран не гаснет), `network.ts` (ждать `online`, Retry-After, канал),
  `progressText.ts` (строка «МБ из МБ · скорость · осталось», причины словами, текст
  окончательного отказа), `videoMeta.ts` (длительность ролика до отправки). Строка на экране —
  `components/UploadProgressLine.tsx` (+ хук `useUploadSpeed`).
- **1. Чтение файла.** Вместо одной попытки — три (пауза 0,5 и 1,5 с); очередь карточки держит
  в памяти исходные файлы заданий этой вкладки и при нечитаемой копии в IndexedDB читает
  исходник и шлёт его. Тексты для человека разные: файла нет / телефон не отдаёт (на Android —
  «сохраните в память или выберите через „Файлы“») / нет места / запрет. В журнал — `e.name`,
  источник (копия/исходник), тип, размер, время изменения, видимость вкладки.
- **2. IndexedDB.** Очередь карточки (`royal-home-uploads` v2) и склад мастера
  (`royal-home-draft-media` v2): файл кладётся в отдельное хранилище `blobs` ОДИН раз,
  статусы/сроки правят только метаданные. Записи v1 читаются как есть и переезжают при
  первой правке или при старте очереди (`migrateLegacyUploadTasks`, по одному заданию на
  транзакцию; не влез — остаётся v1, не теряется). Обновление базы только заводит хранилище,
  данные в нём не переносятся — отказ квоты не обрывает обновление.
- **3. Пауза после отказа сервера.** `workGuard` передаёт повод (`online`/`visible`/`heartbeat`);
  сердцебиение паузу не трогает, `online`/возврат снимают её только у обрыва связи. Вызов без
  повода (явное действие) — как раньше, снимает всё.
- **4.** Сборка ролика мастера — `api(…, { timeoutMs: 120 с })`, общий предел 30 с не рвёт её.
- **5. Размер части.** Проверено: все три клиента частей (`uploadQueue`, `draftUploads`,
  `chunkedUpload`) берут `partSize`/`totalParts` только из плана сервера, своего числа нет
  (на клиенте 8 МБ — только граница пачки ФОТО, не части видео). Менять нечего.
- **6. Общий помощник частями** (`chunkedUpload.ts`: чат, короткий ролик, ролики в соцсети):
  расписание очередей (5 с…5 мин, 10 отказов подряд без продвижения, принятая часть
  сбрасывает счёт), без сети — ждёт `online` (попытки не тратит), 429/503 — не раньше
  Retry-After, старт тоже повторяется, сессия помнится в localStorage по отпечатку
  (сотрудник + адрес + назначение + имя + вес + время изменения, 24 ч) — тот же файл после
  перезагрузки докачивается. Ноль байт части + статус 0 → проверка чтения, не читается — сразу
  понятный отказ.
- **7. Журнал.** Строка `[загрузка]` получила хвост: причина статуса 0 (сеть / тишина в канале /
  обрыв браузером / предел ожидания / сменился сотрудник), номер части, сколько её ушло («ни
  одного байта части»), средняя скорость, тип файла, имя ошибки, источник, видимость вкладки,
  канал (`navigator.connection`). Окончательный отказ («сдалась») пишется всегда — свой запас
  50 записей, не общий предел 20. Пишут теперь все: чат, короткий ролик, соцсети (и фото-пост),
  готовый ролик монтажёра, исходник для перемонтажа.
- **8. Wake Lock** на время отправки (очереди, помощник частями, ролик монтажёра), повторный
  захват при возврате во вкладку, без API — без падения. Подсказка «Не блокируйте экран, пока
  идёт загрузка» — у роликов.
- **9. Закрытие вкладки.** Предупреждение (workGuard) теперь у чата, короткого ролика, роликов и
  фото-поста в соцсети, ролика монтажёра, исходника. Очередь карточки блокирует закрытие, если
  есть задание, не влезшее в IndexedDB; строка такого задания говорит «не закрывайте вкладку».
- **10.** Готовый ролик монтажёра — счёт отказов подряд без продвижения (`planServerRetry`),
  ожидание сети, Retry-After, «Отменить» рвёт отправку по-настоящему (`AbortSignal` в
  `uploadVideoChunked`), «Повторить» докачивает в ту же сессию. `uploadVideoNow` (исходник) —
  повторы по тому же расписанию и настоящая отмена.
- **11.** Короткий ролик: размер (300 МБ) и длительность (5 минут, через `<video>` метаданные)
  — до отправки. Число 300 с сверяется тестом с сервером (`propertyClipVideo.ts`).
- **12.** Одна строка прогресса: короткий ролик, монтажёр (готовый и исходник), пузырь чата
  (ПК и телефон), соцсети (ролик и фото), плитка ролика в мастере (скорость и «осталось»).
  Очередь карточки уже умела — добавлены подсказка про экран и текст «не закрывайте».
- **13.** «Файл мог повредиться» больше не говорим при сбое сети/5xx — текст по причине.
  Отказ чтения пишется в журнал как попытки ЧТЕНИЯ (3/3), а не «1/10» отправки.
- **14.** Удалён `enqueueClipVideo` — его никто не звал (карточка грузит ролик напрямую).
- **Сторож** `npm run audit:upload-xhr` (шаг `precheck` и CI): `new XMLHttpRequest` и
  `upload.onprogress` — только в `lib/upload/` и в четырёх файлах из `.upload-xhr-baseline.json`
  (список только убывает). Тест сторожа — `scripts/audit-upload-xhr.test.mjs`.

## Что осталось / риски

- **Живая проверка на телефонах не делалась**: Android (ролик 200+ МБ из галереи и из
  «Файлов», после перезапуска вкладки), iPhone (блокировка экрана во время загрузки —
  работает ли Wake Lock в установленном PWA), слабый интернет (переключение Wi-Fi/LTE).
- Перенос IndexedDB v1 → v2 на настоящем браузере не проверен (тест — на своём тестовом
  IndexedDB). Худший случай — задание остаётся в формате v1 и грузится как раньше.
- Не сделано: перевод мастера и очереди карточки на общий помощник частями (вторая волна —
  сторож уже держит число реализаций); у очереди мастера в плитке нет обратного отсчёта
  «повтор через N с» (в элементе очереди нет поля следующей попытки).

## Доработка по ревью (26.11)

Независимое ревью волны A, семь пунктов. Тесты — `lib/__tests__/uploadClientReview26.test.ts`
(13 шт.); каждый фикс проверен поломкой (убрал правку — красный).

1. **IndexedDB v1 → v2** (`uploadQueue.ts`, `draftUploadStore.ts`): `onblocked` — понятный отказ
   вместо вечного ожидания (попытка забывается, следующий вызов пробует заново; запоздавшее
   соединение закрывается само); `onversionchange` на открытом соединении — `close()` и сброс.
   `fakeIndexedDb.ts` научен blocked/versionchange (`holdOpen`, `openConnections`), плюс хуки
   `onTx` и `mutate` для гонок.
2. **Wake Lock** (`chunkedUpload.ts`): экран держим, только пока идёт отправка; на ожидании сети
   и паузах повтора снимаем, перед новой попыткой берём заново. (У `uploadVideoNow` и очереди
   карточки блокировка и так жила только внутри отправки.)
3. **«Отмена»** (`api.ts`, `uploadQueue.ts`, `PropertyVideoFixCard.tsx`): `api()` принимает
   `signal` (без него поведение прежнее; отмена даёт `AbortError`, а не «связь прервалась»).
   Старт сессии рвём по сигналу (идемпотентен). Сборку НЕ рвём — сервер мог её выполнить;
   `uploadVideoNow` при созданном ролике отдаёт `ok: true` (сироту убирает карточка), а «Отмена»
   во время сборки показывает «Сборка файла уже идёт — дождитесь окончания».
4. **`migrateLegacyUploadTasks`**: строка читается заново внутри записывающей транзакции;
   убранное задание не воскресает, свежий статус не затирается.
5. **`errorReporter.ts`**: промежуточные отчёты загрузки — свой предел 10, в общий счёт не идут;
   финальные — как прежде (50).
6. **`giveUpMessage` (5xx)**: убрано «о сбое мы уже знаем» (журнал мог не уйти).
7. **`workGuard`**: запись «идёт работа» ставится один раз на весь цикл повторов — и в
   `uploadVideoNow`, и в цикле готового ролика карточки (тот же механизм, найден по классу).

Проверено: `npm run test:web` (484 файла, 3375 тестов), `npm run build:web`,
`npm run map` + `map:check` — зелёные. Не делалось: живой прогон на телефонах.
Не тронуто по заданию: дубли по отпечатку сессии (свойство прежней схемы).
