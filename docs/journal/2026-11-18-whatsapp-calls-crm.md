# 18.11.2026 — Звонки из WhatsApp в CRM: метка, вебхук, сторожа, бот молчит на служебных событиях

- Что изменилось:
  - **Метка канала.** `IncomingCall.source` (`"phone"` | `"whatsapp"`, строка с умолчанием, миграция
    `20261118180000_incoming_call_source` — только `ADD COLUMN … DEFAULT 'phone'`). Решение — одна дверь
    `lib/telephony/callSource.ts`: канал станции `PJSIP/whatsapp-gw-…` = WhatsApp. Значения — `INCOMING_CALL_SOURCES`
    в `packages/shared`. Поле отдают `GET /calls/incoming` и `GET /calls/feed`; метка «WhatsApp»
    (`components/look/calls/CallSourceMark.tsx`) стоит во всех строках входящих: ПК и телефон, «новый вид» и прежний.
  - **Хронология.** «Входящий звонок клиента из WhatsApp: …» — WhatsApp ДОПИСАН после «Входящий звонок», а не вместо:
    по этому началу `lib/noContact.ts` (пропущенный входящий — не контакт агента) и `lib/telephony/callRecordings.ts`
    (поиск записи без добавочного) узнают входящий. Замена слов в начале строки, как предлагалось в задании, молча
    сломала бы оба места; тест держит начало строки.
  - **Карточка незнакомого** по звонку из WhatsApp заводится с источником `WHATSAPP` во всех трёх путях
    (`incomingCalls.ts`, `qualifyIncoming.ts::createClientForCall`, `autoLeadFromCall.ts`).
  - **СМС после пропущенного** (решение владельца): звонок из WhatsApp СМС не получает — одна проверка
    `missedCallFollowup.ts::missedCallSmsSkipForSource`, статус `whatsapp_call` (как остальные отказы — статусом).
    Задача «перезвонить» и пуши остаются как у обычного пропущенного (агенту клиента или общая).
  - **Вебхук, поле `calls`** (`messengers/whatsappCalls.ts`): connect/terminate и статусы звонка — одна строка в
    журнал контейнера (id звонка, событие, номер маской, статус, длительность), без записи в базу. Статусы звонка
    (`value.statuses`, `type: "call"`) больше не попадают в разбор доставки сообщений (`parseStatusUpdates`).
  - **Бот молчит на служебных событиях** (живой случай 18.11: после звонка Meta прислала
    `interactive.call_permission_reply` с `context.id = wacid.…`, бот ответил «не получается открыть вложение»).
    Решение на входе, в `parseIncoming` (им пользуются оба пути приёма — старый и ядро):
    `whatsappServiceEventReason` — `call_permission_reply` и ответ на звонок (`context.id` `wacid.…`) БЕЗ слов и
    содержимого человека → мимо бота, строка в журнале. Текст, голосовое, фото «ответом» на пузырь звонка
    («почему не берёте?») — обычная реплика (правка после ревью). По типам WhatsApp:
    - `reaction` — молчит (было с 01.08.2026);
    - `system` (смена номера и т. п.) — молчит;
    - `request_welcome` (открыл чат, ещё не писал) — молчит;
    - `unsupported` (Meta не смогла передать) — причина по-прежнему в журнал ошибок; событие помечено
      `recordOnly`, и вебхук передаёт его ходу как `silent`: след в переписке CRM остаётся (тот же механизм,
      что у пустой реакции «🔥»), хода бота и ответа нет, «прочитано» не ставится. ОГОВОРКА: это путь LEGACY.
      Если переписку ведёт ядро (CORE), `unsupported` идёт туда как раньше и ядро отвечает своим вопросом
      «Что вас интересует…» (так задумано и закреплено `customer-dm-attachment-postgres.test.ts`); чистого пути
      «записать без хода» в ядре нет — менять его договор ingress в этой правке не стал;
    - `interactive` `button_reply` / `list_reply` — это слова человека: текст = подпись кнопки/строки (раньше тоже
      было «[вложение: interactive]»); `nfm_reply` — текст из `body` (у форм Meta это обычно «Sent» — бот получит
      это слово; оставлено как есть, форм мы не шлём), без `body` — как раньше вложением;
    - `order` (заказ из каталога) — текст человека и id товаров словами;
    - `button` (кнопка шаблона) — без изменений.
  - **Сторож `can_receive_call_sip`** (`lib/whatsappCallingHealth.ts`, крон `whatsapp-calling-health` раз в час):
    звонки и SIP у номера включены, а Meta отвечает BLOCKED или LIMITED — тревога «meta» с кодом и описанием
    Meta; снова AVAILABLE — закрывается сама. Поля `can_receive_call_sip` нет — строка в журнале контейнера, без
    тревоги (открытая не гаснет до настоящего AVAILABLE). Звонки выключены — молчит, запроса о состоянии нет. Сбой самого запроса — своя
    тревога, тоже с автозакрытием. Таймаут 20 с, маркер только заголовком.
  - **Сторож офисного аппарата** (`lib/telephony/officeDeskPhoneWatch.ts`, из `runStationHealthTick` раз в 15 мин):
    приём заведён на аппарат (`incomingPrimaryTarget = "extension"`, 2020), а он не online на станции в рабочие часы
    (Settings.workHoursStart/End по Душанбе, без `companyDaysOff`) две проверки подряд — тревога «Офисный аппарат
    2020 не на связи с ЧЧ:ММ …»; снова на связи — закрывается. Первые 45 минут рабочего дня не судит (утром
    трубку включают не сразу; время в тревоге — с первой проверки дня). Ночью/в выходной и при обрыве связи со
    станцией не судит.
  - **Сообщение автоответчика** после звонка из WhatsApp заводит карточку с источником WHATSAPP
    (`voicemailIngest.ts`: источник берётся у звонка, к которому привяжется сообщение; условие привязки одно —
    `voicemailCallMatchWhere`).
  - **`wa-cert.sh`, режим http** (правка после ревью): в начале каждого запуска снимаются оставшиеся правила
    `rh-wa-acme` (SIGKILL, перезагрузка); удаление только по номеру правила с нашим комментарием (`ufw delete
    allow … port 80` снёс бы и чужое правило); если 80 уже открыт всем чужим правилом — ничего не добавляем и не
    удаляем; флаг «открыто» ставится до `ufw allow`. `renew` передаёт текущий способ проверки (`auth`), так что
    выпущенный через dns сертификат продлевается по http. `wa-health.sh` краснеет, если правило `rh-wa-acme` есть
    вне работающего `wa-cert.sh`. Проверено заглушкой `ufw` (три случая), на сервере не запускалось.
  - `ops/whatsapp-gateway/bin/wa-cert.sh` — режим ACME по http (правка координатора) плюс доработки после ревью выше.
  - **Проверка TLS в `wa-health.sh` и `wa-calling.sh enable` всегда падала** (найдено на сервере 18.11, там
    исправлено руками, здесь — зеркало): `openssl s_client -quiet` включает `-ign_eof`, против Asterisk не
    выходит по концу ввода, `timeout` даёт 124, и с `pipefail` цепочка «ложь» при годном сертификате. Теперь без
    `-quiet`, ищем «Verify return code: 0 (ok)» и `grep … >/dev/null` вместо `grep -q`. Runbook: та же команда,
    режим HTTP-01 (`WA_ACME_METHOD=http`, блок Caddy `http://wa-sip.royalhome.tj` → `acme-webroot`,
    `WA_ACME_EMAIL=none`) и запись о том, что 18.11 звонки у номера нашлись уже включёнными с видимой кнопкой
    (включили в WhatsApp Manager вручную) — выключены и включены по порядку.
  - Миграция переименована координатором в `20261118180000_incoming_call_source` (после
    `20261118170000_seller_automation_switches` из `main`).

  выключен и этого никто не увидел.
