# 13.11.2026 — «Мы написали первыми — человек ответил»: ответ больше не теряется

- Что случилось (прод, 12.11): бот ответил на комментарий в личку или сотрудник
  написал из приложения Instagram; эхо этого НАШЕГО сообщения сохранялось с
  ревизией нового ядра, хотя аккаунт работает на прежнем боте. Когда человек
  отвечал, проверка истории при зачислении считала «его уже ведёт ядро», ход
  вставал HELD, вебхук отвечал Meta 503 «пока не сохранено» 15 минут (31 повтор),
  и Meta выбрасывала сообщение. В журнал ошибок не попадало ничего. В такой
  ловушке сидели 12 человек (10 на royal.home.tj, 2 на arvan__estate).
- Что изменилось:
  - Одна дверь `lib/customerIngressNonInput.ts`: эхо, голая отметка рекламы и эхо
    шаблона — «не ввод клиента», ни одному движку не принадлежат.
  - Проверка истории (`customerAgentEnrollment.ts`, и ветка «ядро», и ветка
    «прежний бот») и сторож прежнего бота (`readCustomerDmSubjectExecution`)
    не считают такие строки владением. Старые строки эха помечены
    `errorCode='provider_echo'`, поэтому 12 человек освобождаются без SQL на проде.
  - Производитель (`customerIngressProducer.ts`): эхо пишется без ревизии и без
    назначения, сразу `HELD/provider_echo`, без задания разбора — гонки «эхо ещё
    не помечено» нет.
  - Постоянный HELD больше не 503 навсегда (`lib/customerRoutingHold.ts`): только
    настоящие гонки (`captured_scope_changed`, `assignment_commit_missing`) отвечают
    503; «уже обработано прежним ботом» — тихий 200; остальное (и любая новая
    причина по умолчанию) — 200 + строка в журнале ошибок на человека «ответьте
    вручную из приложения», директору пуш при первом появлении причины.
    Сообщение при этом по-прежнему не уходит ни ядру, ни прежнему боту:
    «HELD не проваливается в прежний бот» — решение прежних правок, не менялось.
  - Каждый 503 вебхука Meta (личка и комментарии) теперь пишется в журнал ошибок
    с дедупом по причине.
- Почему: потеря первого ответа клиента на проде, задача владельца 13.11.
- Чем проверено: `tests/customer-echo-then-reply-postgres.test.ts` (настоящий
  HTTP с подписью: аккаунт на прежнем боте, аккаунт на ядре, 12 застрявших,
  постоянный HELD при выключенном ядре, 503 с записью в журнал) и
  `tests/customer-routing-hold-disposition.test.ts` (сторож: каждая причина
  HELD цепочки маршрутизации разобрана явно). Каждая проверка краснеет при
  нарочной поломке (8 мутаций: две ветки проверки истории, сторож прежнего
  бота, ревизия у эха, 503 на любой HELD, молчащий журнал, молчащий 503,
  забытая причина). Старые строки эха НЕ правятся (триггер
  `customer_intake_agent_revision_immutable` не тронут, миграций нет): их
  отпускает только проверка истории — это и проверяет тест «12 застрявших».
- `npm run precheck` (13.11, после свода с main #161): сборки shared/api/web,
  все audit-шаги, map:check, сторож карты, сторож журнала, test:scripts
  зелёные; шаг «тесты фронта» трижды красный от таймаутов 5 с при загрузке
  процессора 100 % (в правке нет ни строки `apps/web`; те же файлы с
  `--testTimeout=60000` — 28/28). Полный `test:api` на этой машине не
  гонялся — его гоняет `npm run ship`.
- Что осталось:
  - На проде убедиться (только чтение, с «да» владельца), что у 12 застрявших
    нет строк эха с ревизией и `errorCode` не `provider_echo` (например, задание
    разбора упало и строка осталась RECEIVED/FAILED) — такие всё ещё держат человека.
  - Вероятно тот же класс в комментариях (ОЦЕНКА по коду, тестом не
    воспроизведено, не чинил — нужен отдельный разбор): ответ
    сотрудника через CRM (`STAFF_PUBLIC_COMMENT_REPLY`) делает ветку
    «управляемой», и новый комментарий в ветке без назначения встаёт HELD →
    503 «Комментарий пока не сохранён» на каждый повтор. Причины публичного пути
    сведены в 4 кода (`origin_changed` и т. п.), поэтому отличить постоянное от
    гонки там без переделки нельзя; пока это хотя бы видно в журнале.
  - Запросный уровень (одинаковый MID дважды в одном теле, неизвестный аккаунт)
    по-прежнему 503: подтвердить такое тело нельзя — без свидетеля маршрута оно
    ушло бы в прежний бот. Теперь видно в журнале.

## Второе ревью (13.11, та же ветка)

- Задержанная реплика помечается `heldRouting: true` (`ai/shared.ts`): повтор
  «зависших» (`lib/stuckConversations.ts`) её не выбирает, а сам повтор на такой
  реплике отвечает «не отвечать» — иначе через 5 минут прежний бот заговорил
  бы поверх решения маршрутизации, и так каждые 30 минут.
- Удалённый сотрудником чат не воскресает: нет чата, а у заявки/билета человека
  ссылка на чат обнулена — новый чат не заводится, только строка журнала с
  собеседником. Клиент в корзине: текст ложится в его скрытый чат, никого не зовём.
- Неактивный (уволенный) ответственный не получает уведомление — вместо него
  все, кто читает все чаты.
- Два почти одновременных вебхука больше не дают двойной пуш: перед уведомлением
  атомарная отметка в `ProcessedMessage` (канал `customer-held-notify`, чат + окно 6 ч).
- Скрипт пометки переехал в `apps/api/src/ops/relabelHistoricalEchoTickets.ts`:
  в образе api есть только `dist/`, поэтому запуск — `node dist/ops/relabelHistoricalEchoTickets.js`
  внутри контейнера (точные команды в шапке файла). Копия — через stdout на хост
  в `/backups/crm/` (`--backup=-`), откат — `--restore=-` со stdin. Чтение
  страницами по 500 по `order`, предел `--max-rows` (по умолчанию 50 000) с
  предупреждением и точной добавкой `--after-order=<n>` для продолжения.
- Тесты: задержанная реплика не попадает в повтор и прежний бот не отвечает;
  удалённый чат не воскресает; неактивный ответственный не зовётся; две пачки
  разом — одно уведомление на сотрудника; предел чтения в скрипте.

## Красный ship (облачный прогон 43377387891) — причина и починка

- Причина: правка сочла «постоянными задержками нового сообщения» и те причины
  HELD, которые на деле означают ПОВТОРНУЮ доставку уже известного MID
  (`original_source_changed`, `source_tombstoned_or_ambiguous`,
  `source_assignment_changed`, `original_native_source_already_observed`,
  `historical_legacy_selection_conflict`), а также намеренную границу
  `legacy_native_scope_collision` (тот же человек на другом аккаунте). Для них
  вебхук стал отвечать 200 и записывать текст в чат: повтор старого сообщения
  писался второй раз, удалённый чат заводился заново (надгробие источника
  нарушалось), при смене области у человека появлялся чат. Сторожа
  `customer-original-source`, `customer-agent-legacy-cutover`,
  `customer-public-agent` это и поймали.
- Починка (`lib/customerRoutingHold.ts`): у причины два исхода. «503, ничего не
  пишем» — гонки, повтор MID с уже записанным источником, граница чужого
  аккаунта (как до 13.11, но каждый 503 теперь в журнале). «Записать в чат,
  200, уведомить» — только новое сообщение, задержанное навсегда. Тесты-сторожа
  не менялись; в своём тесте повтор того же MID после записи теперь ожидает 503
  (как любой повтор MID с источником), текст при этом в чате один раз.
- Проверено: три файла из красного прогона зелёные; пять нарочных поломок
  (вернуть любую из причин в «записать») — каждая краснит свой сторож.
  Попутно: две «красные» в локальном прогоне были от мусора в моей тестовой
  базе (17 аккаунтов Instagram без имени после оборванных прогонов →
  `own_identity_registry_incomplete`); на свежей базе зелёные.
- Весь класс тестов, задетых правкой (`node scripts/impact-tests.mjs` по семи
  изменённым модулям — 76 файлов, из них 37 `customer-*-postgres`): все
  зелёные. Подряд в одной базе часть файлов краснеет от остатков друг друга
  (общая политика/ревизия, аккаунты без имени) — каждый такой файл прогнан
  отдельно на свежей копии эталонной базы и зелёный; в CI каждый процесс
  получает свою копию базы.
