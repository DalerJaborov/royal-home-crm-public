# 25.11.2026 — Ролик в мастере объекта получал 502: прокси рвал часть на 10-й секунде

## Корень (ФАКТ, прод, только чтение)

Не выкат и не падение API. В `/etc/caddy/Caddyfile` (глобальный блок `servers`) стоит
`read_body 10s` — потолок Caddy на ВСЁ тело запроса (Go `ReadTimeout`), а не на паузу между
байтами. Часть ролика — 8 МБ; на мобильном канале 2–6 Мбит/с она идёт 11–30 с, и прокси
обрывает её ровно на десятой секунде. nginx контейнера web пишет `400 time=10.000 upstream=-`
(тело до API не дошло), телефон (iPhone, за Cloudflare) получает 502 «Сервер временно недоступен».

Сверка журнала ошибок (`ErrorLog`, UTC) с журналом nginx (`/backups/crm-deploy-logs/royalhome-crm-web-1-20261123-*.log`):

Выкат 50cf9276 в тот вечер: сборка с 17:16:45, перезапуск API 17:19:10, health 200 к 17:19:22
(`journalctl -u royalhome-auto-deploy`) — то есть все 502 до 17:19 пришлись на живой API.
Окно недоступности при выкате ~12 с. «Около 22:16» в постановке — это 17:16 UTC по Душанбе.
Успешные части в те же минуты шли 4–9,3 с — то, что быстрее 10 с, проходило.

Второй дефект очереди мастера (`lib/draftUploads.ts`): пауза считалась от начала захода
(`now + пауза`), а заход с отдачей части длится 10+ с — повтор шёл сразу (в журнале nginx
новая сессия через 2–3 с после обрыва), и 6 попыток сгорали за ~1,5 минуты. И каждый отказ
тратил попытку, даже если за этот заход сервер принял часть (части 2 → 3 → 4 шли вперёд).

## Что изменилось

- `ops/Caddyfile.example`: `timeouts` перенесены в глобальный `servers` (как на проде),
  `read_body 10s` → `5m`. Защита от медленных клиентов остаётся: `read_header 5s`,
  `client_body_timeout 300s` у nginx (пауза между байтами), к origin пускается только Cloudflare.
- Сторож `scripts/audit-limits.mjs`, правило 5: `read_body` шаблона должен вмещать самое
  тяжёлое тело (`request_body.max_size`, не меньше `UPLOAD_PART_BYTES`) на канале 1 Мбит/с.
  Проверен поломкой: с `10s` — красный с номером строки (`scripts/audit-limits.test.mjs`).
- `ops/deploy.sh`: после выката предупреждает, если живой `/etc/caddy/Caddyfile` короче шаблона
  (выкат не валит).
- `apps/web/src/lib/uploadRetry.ts` — одно расписание повторов для обеих очередей
  (5 с … 5 мин, 10 попыток) и правило «часть принята за заход — счёт попыток заново».
  Очередь мастера перешла на него (было 6 попыток, 4–60 с), пауза считается от момента отказа.
  Очередь карточки (`uploadQueue.ts`) берёт то же правило счёта.

## Чем проверено

- `apps/web/src/lib/__tests__/draftUploadsServerRetry.test.ts`: ролик из 12 частей, каждый
  заход одна часть уходит, следующая — 502; доезжает сам. Без продвижения — упирается в потолок
  и ждёт «Повторить». С отключённым правилом тест красный (проверено).
- `apps/web/src/lib/__tests__/uploadRetry.test.ts`, `scripts/audit-limits.test.mjs`, precheck.
- Кусок `ops/deploy.sh` прогнан на подставных файлах: 10s — предупреждение, 5m/10m/500ms/нет файла — тишина.

## Что осталось

- **Ждёт «да» владельца (прод-конфиг):** на сервере `read_body 10s` → `read_body 5m` в
  `/etc/caddy/Caddyfile`: копия `Caddyfile.bak-read-body-<время>`, точная замена строки,
  `caddy validate`, `systemctl reload caddy`, проверка `curl -sI https://crm.royalhome.tj/`.
  Без этого загрузка со слабого канала (Android 1,1–2,8 Мбит/с) продолжит рваться; правка
  очереди лишь даёт ролику доползти, если части проходят хотя бы через раз.
  Настройка общая для всех сайтов этого Caddy (Nuqta, школа) — для них это только послабление.
- Android 24.11: после обрыва — «Телефон не даёт прочитать файл» на шаге сессии. Отдельная
  причина (файл из галереи Android перестаёт читаться), не разбиралась — НЕТ ДАННЫХ.
- Три копии плана частей по 8 МБ (`propertyDraftMedia.ts`, `routes/properties/videos.ts`,
  `UPLOAD_PART_BYTES` в shared) — свести в одну дверь отдельной правкой.
