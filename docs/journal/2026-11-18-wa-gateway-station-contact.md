# 18.11.2026 — шлюз WhatsApp: звонок обрывался через 32 с (ACK не доходил до станции)

## Что было
Первые живые звонки из WhatsApp (16:27 и 16:32 по Душанбе) доходили до офисного аппарата 2020 и
рвались через 28–32 с после ответа. Подробный журнал SIP шлюза (`pjsip set logger on`): станция
отвечает 200 OK с `Contact: <sip:104.145.12.182:5062>` — это `external_signaling_address`
транспорта `0.0.0.0-udp` на станции (FreePBX). Шлюз слал ACK на этот внешний адрес, а не в VPN
(10.9.0.2), станция ACK не получала, повторяла 200 OK и ровно через 32 с (Timer H) присылала BYE
(снят 11:33:02 UTC, BYE станции 11:33:34). Meta и SRTP ни при чём.

## Что изменилось
`ops/whatsapp-gateway/config/pjsip.conf.tmpl`, конечная точка `station`: `rewrite_contact = yes` —
адрес для запросов внутри разговора берётся из источника ответа (10.9.0.2:5062). Конечная точка
`whatsapp` (сторона Meta) осталась `rewrite_contact = no`, как требует Meta. Станцию не трогали
(правка транспорта на Asterisk 16 требует перезапуска станции).

## Чем проверено
На сервере применено 18.11 ~16:35 по Душанбе (пересборка образа `docker compose build`, шаблоны
зашиты в образ). Третий живой звонок владельца 16:36: ACK на `sip:10.9.0.2:5062`, разговор 220 с,
отбой со стороны WhatsApp (Q.850 16), запись `in-+14808647341-20261118-163634-….wav` 3,5 МБ,
строка `IncomingCall` (ответил 2020, 221 с).

## Что осталось
Ничего по этой правке. Вливание в main лишь выравнивает репозиторий с сервером (ops/* автовыкат не
пересобирает).
