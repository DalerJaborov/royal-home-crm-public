# 27.11.2026 — Бот сам догоняет клиента после паузы и сбоя ядра

- Что было (прод 27.11, чтение базы): сотрудник отвечал руками из CRM, бот вставал на паузу (10 минут или час), клиент
  тут же писал вопрос или номер — и бот не отвечал никогда. Переписки af7e2c0a (Facebook, «Без имени», продажа квартиры),
  50a96583 (WhatsApp, Ленинград у мечети), c16141c7, 0d8937c7, c0092e6b. Билеты ядра этих сообщений — HELD,
  `original_context_changed`, без единой попытки: пока пауза, ход не имеет права говорить. После паузы ответить было
  нельзя: срок хода ядра — 120 секунд от получения, подписанный вход живёт 15 минут. Повтор «зависших» для переписок
  ядра ничего не делал: у af7e2c0a четыре задания ai-reply-retry подряд (08:00–09:30 UTC) закончились «ведёт ядро»
  без ответа. Клиентов с агентом повтор пропускал вовсе, и окно у него было «с начала суток по Душанбе».
- Что изменилось:
  1. Часы хода ядра (`lib/customerTurnClock.ts`, одна дверь). У билета появилось поле `resumedAt`: с него ОДИН раз
     отсчитывается новый срок хода того же сообщения. Подлинность входа (подпись Meta, ключ события, порядок) по-прежнему
     сверяется по исходному `receivedAt`. Часы читают: срок жизни входа (`customerIngressAuthority.ts`), пин хода
     (`customerAgentRevision.ts`), время хода и рантайм модели (`customerDmAgentTurn.ts`), память (`customerAgentVerifiedContext.ts`),
     подтверждение передачи сотруднику (`customerHandoverAck.ts` + необязательное `turnClockAt` в общей схеме).
  2. База (миграция `20261127150000_customer_turn_catch_up`): колонка `resumedAt` (не раньше получения и не позже суток),
     проверка пина считает 15 минут от `COALESCE(resumedAt, receivedAt)`, триггер `customer_ticket_resume_once`: часы ставятся
     один раз, только удержанному ходу без закреплённой модели. Пин хода по-прежнему не продлевается никогда.
  3. Сторож `lib/customerTurnCatchUp.ts` (крон каждые 2 минуты, круглые сутки): последнее принятое сообщение переписки ядра,
     удержанное по причине из списка (пауза/смена контекста, сбой хранилища или очереди, версия ядра, просрочка), без ответа
     нашей стороны, пауза кончилась, клиент не просил не писать, переписку не взял агент по объекту, моложе 23 часов —
     возобновляется CAS-ом, задание очереди ставится в той же транзакции. Соседние удержанные сообщения той же пачки
     (10 минут) помечаются `newer_input_resumed` — бот отвечает на всю пачку одним сообщением. Не больше 20 за тик.
     Ход, на котором модель уже закреплялась (так держит ядро `current_artifact_revision_mismatch`), второй раз пройти
     нельзя по устройству ядра: когда пауза только что кончилась, сторож зовёт человека через одну дверь «бот не ответил».
  4. Повтор «зависших» (`lib/stuckConversations.ts`): переписки ядра больше не берёт (их догоняет сторож), клиентов с агентом —
     берёт (правило «бот молчит у агента» отменено 18.09), окно — 23 часа вместо «с начала суток». Повтор помечен `replay` в
     `applyInboundSideEffects`: агенту и хозяину объекта не уходит второй пуш того же сообщения (причина исключения 14.09).
  5. Рубильник «Бот сам догоняет после паузы» (`Settings.botCatchUpEnabled`, ВКЛ), группа «Бот клиентов».
  Номера из таких сообщений попадают в карточку сторожем #497 (`phoneLeadWatchdog.ts`) и самим ходом ядра.
- Чем проверено: `tests/customer-turn-catch-up-postgres.test.ts` на настоящем ядре (подпись, FINAL, пин, очередь отправки):
  ручной ответ → два сообщения клиента на паузе → пауза кончилась → по исходным часам ход «просрочен» → сторож возобновляет →
  ровно один ответ на оба сообщения; второй и третий тик ничего не делают; два сторожа одновременно — одно задание, база
  не даёт второй раз поставить часы; сотрудник ответил после клиента — бот молчит. Тест проверен поломкой: часы без
  возобновления — красный. `inbound-replay-no-push-27-11.test.ts`, обновлён `stuck-conversations.test.ts`.

  ядра; живой проверки на проде нет (после выката смотреть журнал «Бот догоняет: возобновлено ходов N»).
