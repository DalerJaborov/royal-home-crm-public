# 26.11.2026 — Сторож «закрыто по умолчанию» для всех маршрутов сервера

- Что изменилось: новый тест `apps/api/tests/route-access-default-sweep.test.ts`
  обходит ВСЕ зарегистрированные маршруты приложения. (1) Без входа каждый
  маршрут обязан ответить ответом `requireAuth`, кроме явного списка публичных
  `PUBLIC_ROUTES` (у каждого записана причина и своя защита: подпись, ключ,
  токен в ссылке) и вебхуков/витрины по префиксу; устаревшая запись списка
  тоже валит тест. (2) Агент А не видит ни одной метки клиента агента Б (имя,
  номер, текст переписки, заметка звонка, номер собственника) ни в одном
  GET-ответе — ни по идентификатору Б, ни в списках. Внешняя сеть в тесте закрыта.
- Почему: проверка безопасности сервера 26.11. Права стоят внутри каждого
  роутера, а не на общем входе, поэтому маршрут с забытым `requireAuth` открыт
  всем молча. Прежний сторож (`shareholder-read-only.test.ts`) смотрел только
  запись; открытый GET с клиентами или перепиской не ловил никто.
- Чем проверено: тест зелёный на свежем main (3 из 3). Сторож проверен
  поломкой: временный открытый маршрут `GET /districts/zz-open-probe` и снятый
  отказ 403 в `GET /clients/:id` дали ровно два красных теста с этими
  маршрутами; правки откачены. Тем же обходом (вне репозитория) прогнаны роли
  MARKETING, EDITOR, SHAREHOLDER, MANAGER, HEAD_OF_SALES, SECURITY, ADMIN, а
  запись (POST/PATCH/PUT/DELETE) агентом А по данным Б — утечек и чужих
  записей не найдено. Секреты Настроек (все поля SECRET_SETTINGS_FIELDS) не
  попадают ни открытым текстом, ни шифротекстом ни в один GET без параметров
  для ADMIN/DIRECTOR/MANAGER/AGENT.
- Список публичных маршрутов строгий: у каждой записи причина, вид защиты
  из списка GUARDS (подпись, ключ, токен ссылки, токен станции, служебный
  токен, state OAuth, своя cookie, публичные данные) и место защиты в коде
  (файл и функция; тест проверяет, что они существуют). Запись без чего-то из
  этого валит тест — проверено нарочно пустой записью.
- Найдено, НЕ чинено (зона входа, нужно отдельное ревью): счётчик попыток кода
  входа не атомарный — `verifyLoginCode` (lib/loginSmsCode.ts) сначала читает
  `attempts`, потом сравнивает и увеличивает. Параллельные догадки проходят
  проверку `attempts >= 5` все разом; потолок держит только лимитер
  `totpLimiter` (8 за 5 минут на учётку), то есть до 8 догадок на код вместо 5.
  Перебор шести цифр реальным от этого не становится, но правило «5 попыток»
  в коде не выполняется. Лечение: условный `updateMany` с `attempts < 5` до
  сравнения кода.
- Что осталось: обход записи пустым телом не видит маршрутов, где проверка
  тела стоит раньше проверки владельца (22 таких ответа 400, разобраны глазами,
  дыр нет) — для полноты нужен обход с правильными телами.
