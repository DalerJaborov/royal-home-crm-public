# 26.11.2026 — Звонки WhatsApp на второй номер «Арван» (+992 87 791 4444) через тот же шлюз

- **Что изменилось.**
  - Шлюз `ops/whatsapp-gateway`: список номеров бизнеса. Основной — `WA_BUSINESS_NUMBER`, как было;
    дополнительные — `WA_EXTRA_NUMBERS=номер:phone_number_id[:метка]`. `entrypoint.sh` пишет
    `extensions_wa_numbers.conf` (на каждый номер: что набрать станции, имя звонящего, номер для заголовка) и
    собирает свой `[meta-inbound…]` на каждый номер из `secrets/meta/meta_sip_password.<номер>`; основной номер
    читает и прежний файл `meta_sip_password` — шлюз с одним номером работает без правки `gateway.env`.
    Номер без пароля при включённой проверке не пускает никого (защита по умолчанию), `WA_REQUIRE_AUTH=yes`
    требует пароль у каждого номера.
  - Звонок на дополнительный номер шлюз набирает станции его phone_number_id (13+ цифр) с именем
    «WhatsApp Arvan» и заголовком `X-WA-Business-Number`. Станция (`ops/asterisk/extensions_custom.conf`,
    `[from-trunk-whatsapp]`) ловит такие номера шаблоном, ставит `RH_WA_LINE` и ведёт звонок тем же путём, что
    основной; имя «WhatsApp …» сохраняет — агент видит на телефоне, каким брендом отвечать.
  - Скрипты: `--number=<цифры>` у `wa-calling.sh`, `wa-sip-password.sh`, `wa-test-call-button.sh`
    (`wa-lib.sh::wa_select_number`); `wa-health.sh` проверяет `can_receive_call_sip` у каждого номера;
    `graph-call.mjs` пускает не основной номер, только если он заведён строкой канала в CRM, и берёт ключ ЭТОЙ
    строки (`accountTokenById`).
  - CRM: `IncomingCall.waPhoneNumberId` (миграция `20261126190000_incoming_call_wa_line`, колонка
    необязательная); `callSource.ts::whatsappLineFromChannel` — линия из `dialplan.exten` события создания
    канала; бренд — `accounts.ts::whatsappLineBrand` (имя компании строки WhatsApp, иначе её название);
    хронология «Входящий звонок клиента из WhatsApp (Арван): …»; обе ленты звонков отдают `brand`, метка
    «WhatsApp · Арван» (`CallSourceMark`, ПК и телефон).
  - `Dockerfile`: базовый образ прибит к `debian:sid-20261104-slim`. Плавающий `sid-slim` ушёл вперёд снимка
    архива, и сборка шлюза с нуля падала на apt («Unable to satisfy dependencies») — сервер жил на
    закэшированном образе, и следующая пересборка на новом сервере сломалась бы.
  - `scripts/audit-secrets.mjs`: номер WhatsApp «Арван» 877914444 — в списке публичных номеров компании (рядом с
    городским 446501414), иначе runbook с командами для него не проходит сторож номеров.
- **Почему.** Владелец подключил второй номер Arvan (#475); звонки на него шлюз отбивал как «чужой номер», а
  проверка пароля знала один номер.
- **Чем проверено.**
  - `ops/whatsapp-gateway/test/run-e2e.sh` (настоящий Asterisk 22 в Docker, настоящие файлы станции):
    25 зелёных, 0 красных — оба номера со своими паролями, второй доходит до станции с меткой линии
    `1000000000000002` и именем «WhatsApp Arvan», имя второго номера с паролем первого — отказ, основной номер с
    прежним именем файла пароля — как раньше, паролей в журнале нет.
  - Сторож проверен поломкой: прогон, где у второго номера тот же пароль, что у первого, — 24/1, красное
    ровно «пароль первого номера подошёл ко второму».
  - `tests/whatsapp-call-source.test.ts` (11), `tests/calls-wa-line-brand.test.ts` (2),
    `tests/calls-feed-cursor.test.ts` (4); `CallSourceMark.test.tsx`; сборка api/web; `--dry-run` скриптов с
    `--number`.
- **Что осталось (ждёт «да» владельца, по порядку):** runbook `docs/whatsapp-calling-runbook.md`, операция 15:
  15.1 станция → 15.2 шлюз на сервере (`WA_EXTRA_NUMBERS`, `WA_REQUIRE_AUTH=auto`, пересборка) → 15.3 Meta
  enable у Arvan → 15.4 пароль Arvan и `WA_REQUIRE_AUTH=yes` → 15.5 проверочный звонок → 15.6 кнопка.
  Ограничение: звонок, подхваченный досинхронизацией после разрыва связи со станцией, бренда не получит
  (exten уже 6501414) — запишется как на основной номер.
