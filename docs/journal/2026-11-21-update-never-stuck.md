# 21.11.2026 — Вкладка больше не застревает на старой сборке

- **Почему:** iPhone владельца (Safari) больше суток сидел на старой сборке: «Страница
  не найдена» на /ui-check, старый интерфейс, «Входящие загружаем». Ручная перезагрузка
  не спасала.
- **Причина (класс, а не один случай):**
  1. Заголовок `X-App-Build` — момент запуска процесса API, а не версия фронта. Любой
     перезапуск API без смены фронта объявлял каждую вкладку устаревшей → перезагрузка
     в ту же сборку → счётчик попыток рос.
  2. Счётчик (`lib/appUpdateReload.ts`) был привязан только к версии вкладки и без
     срока: после 3 попыток `isUpdateLoopSuppressed` → `true` навсегда, обновление
     молчало, на экране не было ничего. В Safari sessionStorage живёт днями.
  3. Идущая «работа» (`lib/workGuard.ts`) держала вкладку от обновления без потолка;
     открытый мастер объекта с полями держит запись всё время, пока открыт.
- **Что изменилось:**
  - Решает только `/version.json` (версия фронта против `__APP_VERSION__`). Смена
    `X-App-Build` лишь будит проверку (`lib/appVersion.ts` → `checkAppVersionNow`).
    Опрос не останавливается после первого расхождения, ловит смену цели и откат.
  - Счётчик — окном: не больше 3 попыток за 10 минут на пару «моя сборка → сборка
    сервера»; новая сборка сервера — счёт с нуля; запись старого вида игнорируется.
  - Исчерпаны попытки — плашка «Есть обновление · Обновить» (`components/UpdateBanner.tsx`,
    токены нового вида с запасными значениями, видна и на /login), кнопка — полный
    сброс (воркер, кэши сборки, свежий адрес), сам повтор — когда окно освободится.
    Сдача уходит в журнал один раз на пару.
  - Проверки `/version.json` ещё и на `pageshow` (возврат из bfcache в Safari) и `focus`;
    пока вкладка видима — `registration.update()` раз в минуту.
  - Потолок ожидания долгой работы — 15 минут, затем `flushWork()` и обновление.
    Очереди файлов живут в IndexedDB (`uploadQueue.ts`, `draftUploadStore.ts`) и
    продолжаются после перезагрузки. Исключение: ролик тяжелее 300 МБ в черновике
    мастера в IndexedDB не хранится (так было и до правки).
  - Шаг решения вынесен в `lib/appUpdateFlow.ts` (без React) — его можно тестировать.
  - Сервер: заголовки `X-Client-Build` / `X-Client-Build-Time` от вкладки;
    `apps/api/src/lib/clientBuildWatch.ts` раз в час тихо (без пуша) пишет в журнал
    сводку «вкладки на старой сборке дольше 30 минут после выхода новой».
  - Подмена воркера и перезагрузка по-прежнему одно движение (vite.config.ts) — не тронуто.
- **Чем проверено:** vitest `appUpdateReload`, `appVersion`, `appUpdateFlow` (тест класса:
  три смены X-App-Build без смены фронта не дают ни попытки, ни блокировки; после
  трёх попыток — плашка; новая сборка сервера сбрасывает счётчик; откат гасит плашку;
  потолок 15 минут), `UpdateBanner`, api `client-build-watch.test.ts`; сторож окна
  проверен внесением поломки (окно → бесконечность: 3 теста красные). e2e
  `app-update-never-stuck.spec.ts` — подменённая version.json → плашка → кнопка.
- **Что осталось:**
  - Вкладки, уже заблокированные СТАРЫМ кодом, сами не выйдут: старый код ничего не
    покажет. Владельцу один раз — закрыть вкладку CRM в Safari (или все вкладки CRM)
    и открыть заново; новая вкладка получит новый код.
  - `X-App-Build` по-прежнему время старта API; делать его версией фронта без правки
    `ops/` нечем. Не нужно: теперь это только подсказка.
