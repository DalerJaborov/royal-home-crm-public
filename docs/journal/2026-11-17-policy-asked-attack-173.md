# 17.11.2026: условия компании только на вопрос клиента + атака F1-F19 (перенос из старого PR #173)

Старый PR #173 «Ядро бота: знания «Обучения»» устарел: с тех пор в main вошло «один мозг» (#211/#238/#213/#223). Из него перенесены только две части, всё остальное (комиссия по роли, роль-вопрос, приветствие один раз, пара V3, новые хеши промпта и знаний) сознательно НЕ тронуто.

## Что изменилось

1. **Условия компании только на собственный вопрос клиента** (`apps/api/src/ai/customerAgentPolicyAsked.ts`, одна дверь `customerPolicyTermAsked`).
   - В main уже было закрыто для `legal` и `rental` (регулярки `customerLegalAsked` / `customerRentalAsked`) и для `service_scope` (`serviceScopeLines`). Не было для `commission`, `payment`, `negotiation`: модель могла прочитать условие, и рендерер печатал его на «адрес этого дома?».
   - Теперь дверь отвечает по словам клиента (`clientOwnWords`, голос: по расшифровке), решает сервер, не модель. `legal`/`rental` делегируют прежним проверенным регуляркам, остальные темы разобраны в новом файле.
   - Рендерер (`customerAgentRenderer.ts`, цикл по `company_policy`): в личке строка условия печатается только на вопрос; в публичных комментариях и при рендере без текста клиента (память) всё как было.
   - Если из ответа выпали одни непрошеные условия: известная роль получает следующий шаг (`nothingNewLine`), без роли один вопрос о теме «недвижимость или работа?». Не молчание и не свалка условий.
   - Строка комиссии без длинного тире: «Комиссия для продавца 2%, для покупателя 0%.» (`no-em-dash` из судьи ловил её).
   - Менялся код рендерера, значит меняется `rendererHash`. Промпт и знания не менялись.
2. **Стенд атаки**: сценарии `learning-f01`...`learning-f19` (корпус buyer/job/language/seller/multi-turn), правила судьи `no-em-dash` и `no-greet-after-first` (+ тесты судьи), телефон рекрутёра в допустимых фактах стенда. Всё на скриптовой модели, без платных вызовов и без живого ключа.

3. **Доводка после свода со свежим `main` (17.11, вечер).** Свод чистый, конфликтов нет (`customerAgentRenderer.ts` в `main` с момента ответвления не менялся). Прогон соседних тестов нашёл две настоящие поломки и одну устаревшую проверку:
   - **Две копии одного определителя.** `customerAgentSellerGuard.ts` держал свой `COMMISSION_ASK` и понимал «Чи шарту шароит доред?» / «какие у вас условия?» как вопрос о комиссии (живой случай FB 16.11 17:44) и заставлял ядро прочитать комиссию, а новая дверь рендерера этих слов не знала и выбрасывала прочитанную комиссию как непрошеную: продавец снова получал вопрос вместо условий (`customer-seller-terms-fb-16-11`). Теперь детектор один: `customerCommissionWordsAsked` и `customerAgencyTermsAsked` в `customerAgentPolicyAsked.ts`, сторож продавца зовёт их. Попутно сторож продавца стал видеть только слова самого клиента (`clientOwnWords`) и латиницу.
   - **«Фаҳмидам» после уже сказанной комиссии** получал «амвол ё кор?» вместо подтверждения (`customer-bot-8-chats-15-11`, ревью С1). Если непрошеное условие уже звучало в этом чате, клиент откликается на него: ответ прежний (`nothingNewLine`), вопрос о теме только когда условие новое.
   - `customer-agent-public-reads`: проверка ждала строку комиссии с длинным тире; переписана на новую строку без тире.
4. **Находка ревью #269.** Сообщение целиком из слова условий без «?» («условия», «Условия.», «шартҳо», «шароит», «шарту шароит», «шарт») не считалось вопросом, и рендерер выбрасывал комиссию, которую до ветки печатал. Теперь одно-два таких слова и больше ничего это вопрос об условиях. Заодно сужено: «условия» считается вопросом только внутри своей части фразы, поэтому «мне условия не важны, сколько комнат?» комиссию не получает (раньше «?» и «сколько» искались по всему сообщению). Тесты проверены внесением поломки.

## Зачем

Живые случаи 13-14.11: условия торга на вопрос об адресе, «нет рассрочки» на присланную картинку, пустой ответ вместо вопроса (`job-unknown-003`). Класс один: условие печатается по выбору модели, а не по вопросу клиента.
