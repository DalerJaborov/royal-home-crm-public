# Покупатель и продавец: отдельные факты, решения и исполнение

Продолжение сверки PDF и голосовых с существующими путями CRM. Согласованные исключения: личный номер агента в публикации сохраняется; восстановление сначала действующему прежнему агенту, иначе обычная автоматическая раздача; сроки РОПа настраиваются перед запуском без выдуманных значений. Подтверждение одного факта не означает С4. Отсутствие ответа и невыясненный результат опроса различаются.

Добавлены отдельные журналы будущих источников: кандидаты показа, переносы приёмки, факты назначения и доставки. Старые даты и слова сотрудников не становятся новыми доказательствами. Показ требует времени и объекта либо явного описания объекта вне CRM. Неуказанное время не подменяется полуднем. Дополнительные номера извлекаются только из подходящего собственного источника с сохранением происхождения.

Новые контуры включают предпросмотр проверок собственника от отправки и ручного создания, единое досье снятия объекта, внутренние аналоги цен предложений, доставку выбранной озвучки и месячный отчёт собственнику с квитанциями. Исполнение отделено от плана: PREVIEW не превращается в отправку после смены серверного флага; неизвестный исход требует сверки. Сетевые вызовы выполняются вне транзакционных блокировок.

Будущие автоматические задачи покупателя и продавца используют одну машину рабочих сроков, получения и действий РОПа. До включения задаются сроки и действующий руководитель; серверные допуски и даты начала обязательны. Режим источника сохраняется при его записи. Старые PREVIEW не повышаются до LIVE. Задержка worker не создаёт уже просроченную первую задачу. Подтверждённый записью новый перенос приёмки прекращает только дополнительные задачи прежнего эпизода; одинаковая дата не сбрасывает срок. Одновременные противоречащие источники не упорядочиваются случайными идентификаторами.

Приватные недельные обзоры охватывают отложенные после показа карточки, отсутствие записанной активности объекта и незавершённую бронь/сделку. Это чтение, без изменения «Отложенных». Совпадения названий сторонних агентств за 90 дней сохраняют исходные метки: совпадение текста не доказывает идентичность компании. Сводки ручных контактов и неподтверждённых отправок показывают пределы локального журнала. Неизвестная полнота каналов не превращается в доказанный «карманный показ».

Приватные операции, старые связанные ошибки и уведомления фильтруются до счётчиков, пагинации и действий. Обычные отчёты исключают проверки; исторические снимки сохраняются и получают безопасную публичную проекцию. Изменения настроек проверок имеют отдельный приватный аудит. Исправление имён через maintenance CLI требует предварительного плана и проверки текущего источника, не разрешает произвольный SQL или смену статусов/владения.

Проверки: изолированная PostgreSQL, синтетические карточки и подменённые внешние провайдеры. Применение новых миграций и сравнение схемы на отдельной базе выполнены; итоговые номера прогонов и точный коммит фиксируются в отчёте PR после завершения общего прогона. Этот журнал не является заявлением об успешном полном прогоне или выпуске. Продакшен, реальные отправки, оплачиваемая генерация и повторная очистка старой истории в этот этап не входят. RU/TJ пилот и наблюдение за шумом требуют отдельного запуска.

По результатам полного облачного прогона исправлены совместимость прежних тестовых данных с обязательными временем/объектом показа, прямая запись исторического владельца вне центральной операции и транзактное сохранение дополнительного номера (Prisma не читает PostgreSQL `void`: блокировка теперь возвращает поддерживаемый `SELECT 1`). Расчёт статистики использует чистый модуль времени показа, не импортируя модуль звонков в worker. Законный ответ на сохранённый вопрос о собственном дополнительном номере проверяется в контексте диалога; ограничения чужих номеров сохранены. Служебные checkpoint-идентификаторы исключены из сканера секретов только по трём точным историческим совпадениям, без отключения правил.

Отдельно подтверждено владельцем: при восстановлении карточки замороженный прежний агент исключается, в том числе при отпуске/больничном. Далее выбирается доступный записанный владелец или обычная AUTO-очередь. Это не меняет защиту уже действующих карточек при обычной заморозке сотрудника.

## Final permission and restoration variant review

Independent read-only review of frozen source 441ef24 found two additional blockers before release: the manual trash-restore endpoint still retained frozen owners, and several private direct/projection routes checked the ADMIN/DIRECTOR ceiling without the effective securityReview grant. These findings supersede any earlier statement that all variants were closed.

Manual restore now applies the same active sales-role/non-frozen eligibility to current and historical owners, rechecks the selected agents under transaction locks, and preserves completed-assignment/deferred markers. The current owner of an already active card is not moved merely for absence.

Private request access is centralized in auth/investigations.ts: both the role ceiling and effective clients.securityReview are required. Query, DTO, timeline, aggregate, calendar, audit, lesson/case/settings history and inbox callers pass the effective investigation viewer role before counts and pagination. Private push recipients are recomputed from current role and resolved permissions; already-open private voice streams recheck effective permission at heartbeat. Ordinary public records and operational notices remain visible.

Actual PostgreSQL receipts: effective-private-regressions.log 7 files/61 assertions PASS; revoked-primary-surfaces-test.log 1 file/3 assertions PASS (including same-token revocation, grant ceiling, counters and recipient selection). API/shared build PASS. The preservation batch initially found one stale recipient mock missing the newly selected role/permissions fields; corrected without weakening the production filter, separate recipient rerun PASS. Final combined source/cloud verification remains required for the new commit.

## Additional isolated acceptance — saved control configuration
Expanded browser acceptance reproduced a data-preservation defect: saved control deadlines/ROP were described correctly but editor controls reset to blanks after reload. Editing only required deadlines could therefore drop the optional follow-up/ROP. The editor now derives its untouched values from persisted configuration, retains an in-progress draft during query refreshes, and resets that draft only after successful config save/refetch. No defaults or execution gates changed. Before-patch SSR regression failed, after-patch both configured/unconfigured checks pass; actual isolated browser/API save/reload preserves unchanged optional values.

The additional all-route desktop/mobile pass and backup/restore rehearsal use synthetic local data with external fetch blocked. They are separate acceptance evidence, not production delivery or a substitute for an approved RU/TJ voice pilot.

## Owner decision: editable starting timings
The owner subsequently requested practical starting values instead of leaving all timing fields blank. The form now offers2 working days for agent work,1 for ROP receipt,2 for ROP action and2 for buyer-candidate follow-up after the original3-day wait. These are an editable proposal, never an implicit backend configuration or permission to activate execution. Existing persisted custom values and intentionally absent optional fields retain precedence. No real staff identity is selected automatically. A starter action preserves an already selected manager; saving remains explicit and all server gates stay unchanged.
