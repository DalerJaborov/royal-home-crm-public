Источник: независимый аудит системы вокруг звонка (11.11.2026, ветка `origin/feat/voice-el-ready-11-11`
@2466ffb8) и решение владельца о «пяти опорах». Метки: ФАКТ (файл:строка) / ОЦЕНКА / НЕТ ДАННЫХ.

**Правило плана:** пачка = одна ветка = один исполнитель, ≤ ~10 файлов. Две пачки не владеют одним
файлом одновременно; где без общего файла не обойтись (мост `liveVoiceBridge.ts`, `routes/settings.ts`,
`prisma/schema.prisma`), владение идёт **по очереди**, и пачка трогает только названную функцию.

звонка на номер владельца после них.

## 2. Пачки

### Волна 1 — блокеры (параллельно, общих файлов нет)

**П1. «Не набирать в тишину»** — architect, M (~400 строк)
- Цель: исходящий звонок не набирается, если выбранный поставщик сейчас не поднимется; отказ ElevenLabs
  посреди подъёма — этот звонок идёт через Gemini, а не в тишину; откат на Google действует сразу; кеш
  подготовки агента прогрет до первого звонка.
- Как: (1) `probeLiveVoiceProvider()` — для ElevenLabs запрос signed URL с потолком 3 с, итог кешируется
  на 60 с; вызывается в `originateLiveVoiceScenarioCall` и `originateLiveVoiceCallToClient` рядом с
  `liveVoiceGeminiPaused()`; отказ → `busy` (вызывающий переносит, попытку не тратит). (2) В
  `prepareModelPart`: отказ `connect` у ElevenLabs при `!ctx.failed` → один заход через `LiveVoiceClient`
  (Gemini) в остатке потолка подъёма, причина в журнал `elevenlabs-fallback-google`. (3) Пауза — по
  поставщику (`pausedUntil[provider]`), смена поставщика в Настройках снимает её. (4) Прогрев:
  `ensureElevenLabsAgentReady` для каждого набора функций при старте api и по кнопке «Проверить агента»
  (кнопка зовёт тот же путь, а не `syncElevenLabsAgentDetailed` напрямую).
- Файлы: `ai/liveVoiceProvider.ts`, `lib/telephony/liveVoiceBridge.ts` (только `originate*`,
  `prepareModelPart`, пауза), `routes/settings.ts` (только `/live-voice/elevenlabs-check` и сохранение
  `liveVoiceProvider`), `index.ts` (прогрев), тесты ×3.
- Тесты/сторожа: отказ signed URL → `busy` и ни одного Originate; отказ connect ElevenLabs → сессия на
  Gemini, человек в мосте; две неудачи ElevenLabs + переключение на google → следующий звонок не на
  паузе; после кнопки «Проверить» звонок не делает ни одного PATCH. Каждый сторож проверить нарочной
  поломкой.
- Зависимости: нет. Мост после П1 переходит к П3.

**П2. «Свои функции у каждого вида звонка» + хранение** — architect, M (~300 строк)
- Цель: у каждого вида звонка ровно его описание `end_call`; агент не кладёт трубку встроенной функцией
  мимо CRM; разговоры у ElevenLabs хранятся не дольше N дней.
- Как: функции заводятся **по содержимому**, а не по имени: ключ = имя + хеш описания и параметров,
  поиск существующей по полному совпадению `tool_config`, иначе POST новой; подмена `tool_ids` на звонок
  уже есть (voiceClient:322–330). НЕТ ДАННЫХ, разрешает ли ElevenLabs две функции с одним именем в
  кабинете — первым шагом проверить `voice:patch-check` на тестовом агенте; если нет — запасной путь:
  имя `end_call_<вид>` на стороне ElevenLabs и обратное сопоставление имени в `elevenLabsVoiceClient.ts`
  (мост и персоны не трогаются). Встроенный `built_in_tools.end_call` в настройке агента выключить (трубку
  кладёт мост, как у Gemini) — после проверки на тестовом агенте. `platform_settings.privacy.retention_days`
  (значение — решение владельца, предложение 30).
- Файлы: `ai/elevenLabsAgentSync.ts` (функции синхронизации и белый список PATCH; **константу
  `ELEVENLABS_PHONE_AGENT_TUNING` в части звучания не трогать** — её ведёт `feat/voice-tajik-speech-11-11`,
  сводить по очереди вливания), `ai/elevenLabsVoiceClient.ts`, `scripts/elevenlabs/patch-check.mjs`,
  тесты ×2.
- Тесты/сторожа: подготовка приглашения → опроса → приглашения даёт приглашению его же `end_call` (id
  разные или описание своё); тест-сторож: у всех наборов функций (`CONSULTANT_TOOLS`, `LIVE_VOICE_TOOLS`,
  `POST_SHOWING_CALL_TOOLS`, `INTERVIEW_INVITE_CALL_TOOLS`) одинаковое имя с разным описанием не может
  получить один id; PATCH несёт `retention_days`.
- Зависимости: нет; согласовать порядок вливания с tajik-веткой (общий файл).

### Волна 2 — защита людей и денег (после П1)

**П3. Одна дверь «можно ли звонить» (`robotCallPolicy`)** — architect, M (~500 строк, миграция)
- Цель: любой набор роботом (сценарий, карточка, рекрутинг, проверочный — с исключением только для
  часов) проходит одну функцию: часы и выходные Душанбе + праздники, единый «не звонить» (по номеру и по
  человеку), чёрный список станции, частота на номер (предложение: ≤ 1 звонок робота в сутки и ≤ 3 за 7
  дней на номер по всем видам вместе — числа утверждает владелец).
- Как: модель `RobotCallStop` (номер в 9 цифр, clientId?, источник: переписка / голос / сотрудник /
  станция, кто, когда) — единое хранилище; `scenarioCallBlockReason` переезжает внутрь политики; частота —
  по `LiveVoiceSession` исходящим за окно. Вызов политики — внутри `originate*` моста (одно место), не у
  вызывающих. Поле `Settings.companyHolidays` (даты) — в ту же проверку часов. Ручка API «не звонить»
  на карточке + переключатель в карточке (ПК + телефон одним экраном).
- Файлы: `prisma/schema.prisma` + миграция, `lib/robotCallPolicy.ts` (новый),
  `lib/scenarioCallEligibility.ts` (обёртка над политикой), `lib/telephony/liveVoiceBridge.ts` (только
  `originate*`), `routes/clients/communications.ts`, `apps/web/src/pages/ClientDetail.tsx` (или текущий
  файл карточки), `packages/shared/src/robotCallPolicy.ts` (схема), тесты ×2.
- Тесты/сторожа: звонок по карточке в 23:00, по номеру со стопом, по номеру из чёрного списка — отказ
  без Originate; четвёртый звонок за неделю — отказ; **сторож архитектуры**: `originateToStasisApp`
  зовётся только из моста, и каждая `originate*` в мосте зовёт политику (тест читает исходник).
- Зависимости: П1 влита (мост). Мост после П3 → П6.

**П4. «Не звоните» голосом, автоответчик, предупреждение о записи** — coder, S–M (~250 строк)
- Цель: «не звоните мне» в любом звонке робота ставит стоп из П3; автоответчик опознаётся и звонок
  заканчивается за ≤ 10 с без разговора с ним; в начале разговора одна короткая фраза о записи (текст —
  владелец; ru и tg через `tajik-phrasebook`).
- Как: причина `do_not_call` в `end_call` всех видов + разбор расшифровки как запасной путь; запись стопа
  в обработчиках итога; детектор автоответчика — в мосте по первым словам + причина `voicemail`.
- Файлы: персоны ×4 и `liveVoiceConsultant.ts` (после вливания prompt-gaps), `lib/postShowingCall.ts`,
  `lib/sellerProbeCall.ts`, `lib/recruitmentCommunications.ts` (итог), тест.
- Тесты: «больше не звоните» в каждом виде → стоп записан, следующий набор отказан политикой П3.
- Зависимости: П3, `fix/voice-robot-prompt-gaps-11-11` влита.

**П5. Потолок минут и учёт расхода** — coder, S–M (~300 строк, миграция)
- Цель: робот (входящие и исходящие вместе) не тратит больше N минут в сутки по Душанбе и M в месяц;
  на 80 % месячного запаса — одна тревога директору; минуты ElevenLabs видны в журнале расходов ИИ.
- Как: `lib/telephony/robotMinutes.ts` — сумма длительностей `LiveVoiceSession` по поставщику за сутки и
  месяц; проверка в политике П3 (исходящие) и при приёме входящего (входящий сверх потолка — на
  автоответчик станции); запись звонка ElevenLabs в журнал ИИ отдельной меткой `:elevenlabs-minutes`
  (минуты, а не токены — не выдумывать цену Gemini). Поля `Settings.robotDailyMinutesCap`,
  `robotMonthlyMinutesBudget` + строка в Настройках.
- Файлы: `prisma/schema.prisma` + миграция (после П3), `lib/telephony/robotMinutes.ts`,
  `lib/robotCallPolicy.ts` (одна проверка), `lib/telephony/liveVoiceBridge.ts` (только приём входящего и
  запись расхода в `endLiveVoiceSession`), `routes/settings.ts` (поля), экран Настроек, тест.
- Тесты: потолок достигнут → исходящий не набирается, входящий отдан станции; тревога одна за месяц.
- Зависимости: П3 (политика и схема).

### Волна 3 — пять опор

**П6. Бриф звонка и память (опоры 1 и 4)** — architect, M (~450 строк)
- Цель: перед каждым звонком у модели одна короткая карточка: кто (имя, как обращаться), одна цель
  звонка, что уже знаем (итоги прошлых звонков робота, последние сообщения переписки, объекты в работе) —
  не длиннее ~1500 знаков; чужих данных нет (см. П9).
- Как: `lib/telephony/callBrief.ts` — сбор по `kind` + `clientId`/`jobApplicationId`/номеру; вставка
  блока в промт в одном месте моста (`prepareModelPart`), а не в каждой персоне; потолок размера и
  очистка текста (`promptSafeText`). Память прошлых разговоров = итоги из П7.
- Файлы: `lib/telephony/callBrief.ts` (новый), `lib/telephony/liveVoiceBridge.ts` (только
  `prepareModelPart`), `ai/contactProfileBlock.ts`, тест ×2.
- Тесты: бриф каждого вида не содержит полей из запретного списка П9; второй звонок тому же человеку
  содержит итог первого.
- Зависимости: П7 влита (мост по очереди; память прошлых звонков — итоги П7).

**П7. Итог звонка в CRM и хронологию (опора 1)** — architect, M (~400 строк)
- Цель: после ЛЮБОГО звонка робота (включая карточку и входящий) — одна запись в хронологии нужной
  карточки (клиент / анкета кандидата / объект): исход одним словом, сводка 1–3 строки, ссылка на запись
  и расшифровку; результат не теряется при обрыве и выкате; повторная доставка итога не дублирует запись.
- Как: `lib/telephony/callOutcome.ts` — один обработчик после `endLiveVoiceSession`, идемпотентный по
  `LiveVoiceSession.id` (уникальный ключ записи хронологии); сводка — разбор расшифровки (дешёвая модель,
  таймаут, отказ → «итог не разобран» + запись есть); итог, не записанный при выкате, добирает уборщик по
  `LiveVoiceSession.endedAt` без записи.
- Файлы: `lib/telephony/callOutcome.ts` (новый), `lib/telephony/liveVoiceBridge.ts` (одна строка-крючок
  в `endLiveVoiceSession` — после П5), `routes/clients/communications.ts` (убрать «запущен» как итог),
  отображение в хронологии карточки (web, ПК + телефон), тест ×2.
- Тесты: два вызова итога → одна запись; обрыв на выкате → запись добрана тиком.
- Зависимости: П3 (communications.ts по очереди), П5 (мост по очереди). Идёт раньше П6: бриф берёт память из итогов.

**П8. База знаний компании (опора 2)** — coder, M (~350 строк, миграция)

**П9. Окна доступа по виду звонка (опора 3)** — architect, M (~400 строк)
- Цель: функции каждого вида звонка видят только своё окно: нет телефона собственника, других клиентов,

- Файлы: `lib/telephony/callWindows.ts` (новый), `lib/telephony/liveVoicePropertyTools.ts`,

**П10. Ответ < 1 с и выживание гудков (опора 4)** — architect, L (~600 строк)
- Цель: у исходящего голос подключается ВО ВРЕМЯ гудков, а не после «алло» (сейчас до 25 с тишины в
  худшем случае); задание звонка переживает перезапуск api во время гудков.
- Как: подключение поставщика сразу после Originate, сессия ждёт StasisStart; не ответили за 30 с —
  сокет закрывается (минута ElevenLabs не тратится: ОЦЕНКА, проверить по кабинету); задание звонка — в
  базе (`channelId` уже передаётся у рекрутинга), а не только в `pendingOutboundCalls`. Замер: время от
  ответа до первого слова в `liveVoiceMetrics`.
- Файлы: `lib/telephony/liveVoiceBridge.ts` (подъём исходящего — после П6), `lib/telephony/liveVoiceMetrics.ts`,
  `prisma/schema.prisma` (после П8), тест ×2.
- Тесты: от «ответил» до первого кадра голоса в тесте с поддельным поставщиком < 1 с; перезапуск во
  время гудков → ответивший не обрывается молча.
- Зависимости: П1, П6 (мост по очереди). Человечность в словах (короткие фразы, перебивание, «помощник компании») — в
  `fix/voice-robot-prompt-gaps-11-11` и `feat/voice-tajik-speech-11-11`, здесь не дублируется.

**П11. Передача живому агенту и задача «перезвонить» (опора 5)** — architect, M (~400 строк)
- Цель: в исходящих звонках (не только у входящего консультанта) робот по просьбе человека переводит на
  свободного агента; агента нет — задача «перезвонить» на ответственного со сводкой и ссылкой на
  запись; никаких обещаний сроков (см. `timePromiseGuard`).
