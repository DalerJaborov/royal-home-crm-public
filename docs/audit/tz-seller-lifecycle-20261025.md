## Лестница контроля

`sellerControlMachine` — чистая машина состояний. `sellerControlEpisodes` —
транзакционная запись эпизодов/событий с блокировкой Client → Episode, revision CAS,
идемпотентностью requestKey. Один эпизод на назначение и режим исполнения;
закрытый эпизод не воскрешается повторным запуском. Изменение назначения отменяет эпизод.

Только выбранная текущая карточка с достоверным недостатком объектов может начать
эпизод. Черновики не считаются принятыми. Нет автоматического исторического сканирования.
Сроки всех трёх этапов задаются явно. Пустая настройка = NOT_CONFIGURED, без переходов
по сроку. Используется календарь компании/получателя; срок следующего этапа начинается
при его создании, а не задним числом.

AGENT_TASK → ROP_RECEIPT → ROP_ACTION → DIRECTOR. Отсутствие подтверждения получения
и отсутствие подтверждённого результата различаются. Запись действия не продлевает
срок бесконечно и не доказывает результат. Дополненный перечень закрывает эпизод.
Неизвестные факты/недоступность данных не считаются бездействием или виной.
Ни баллы, ни обвинения, ни внешние отправки машина не создаёт.

При переходе LIVE эпизода к директору в той же транзакции создаётся одно закрытое
уведомление в существующей ленте каждого активного ADMIN/DIRECTOR с правом закрытых
проверок. Это INSIGHT без push и внешней доставки, с фактическим описанием отсутствия
отметки/результата. Идентификаторы уведомлений и получателей сохраняются в событии
эпизода; `read` означает только открытие, не решение. Повтор сохраняет прочитанность
и время исходной записи. Уведомление не порождает новое дело/доказательство.
Отсутствие подходящего руководителя откатывает переход: он повторяется после
устранения причины, без ложной квитанции доставки. Моделирование уведомлений не создаёт.
DIRECTOR эпизоды также проверяются на завершение назначения/работы и полный перечень
объектов. Стабильная постраничная обработка не позволяет ожидающим эпизодам блокировать
проверку последующих; сменивший роль руководитель не может подтверждать старую задачу.

API `/security/cases/seller-control` и панель доступны только ADMIN/DIRECTOR.
API всегда создаёт PREVIEW; события имеют префикс SIMULATED, режим строки неизменяем.
Моделирование создаёт ноль обычных задач. Настройка сроков не активирует исполнение.
Внутреннее LIVE исполнение дополнительно требует серверного допуска
`SELLER_CONTROL_INTERNAL_LIVE=explicitly-approved`; этот допуск не включался.
`runSellerControlTick` обрабатывает только уже явно созданные LIVE эпизоды.
Реальный ответ руководителя `/interactions/:id/work-response` требует точного
назначения ему обычной задачи; ответ не содержит episode id, событий или признаков проверки.
Закрыть или прекратить LIVE контроль могут ADMIN/DIRECTOR через закрытый API,
если серверный допуск включён. Режим берётся из строки, не из запроса. Этот путь
не позволяет подменить реальное получение/действие руководителя моделированием,
не меняет вердикт проверки, баллы или владельца клиента.

## Проверки и ограничения

Новые pure/mocked suites: `seller-control-machine`, `seller-control-episodes`,
`seller-control-routes`. Доказательство выполнения и сборки ведёт координатор отдельно;
само наличие этих тестов не означает успешный прогон или производственный запуск.
Внешняя доставка не проверялась и не включалась. Все реальные отправки запрещены
в этой работе. Уведомления и cron запуск требуют отдельной проверенной интеграции;
PREVIEW записи никогда не превращаются в реальные автоматически.
